# ゲーム状態を使う追加リソース活用の実装計画

> 後続の実装担当は、タスクごとの手順を `superpowers:executing-plans` または `superpowers:subagent-driven-development` で進める。

**目標**

RimWorldが保持するマップ・物資・セーブのデータを、プレイ中の可視化、集計、読み込み準備に使う。WOWGAG・Axen・Overclockと併用しながら、CPU、RAM、GPU、VRAMを使える入口を追加する。

**対象環境**

Windows版RimWorld 1.7.5011 rev24、.NET 10、Waylith。MoreUseResourcesの[併用計画](2026-11-17-performance-mod-resource-coexistence-ja.md)と[併用設計](../specs/2026-11-17-performance-mod-resource-coexistence-ja.md)を引き継ぐ。

**採用条件**

静的確認でリソースを実際に使う経路があり、結果をゲーム内の表示・集計または既存ローダーが使える見込みがある候補を実装する。性能改善や実用性の事前実証は採用条件に含めない。完了確認は単体テスト、静的なAPI照合、Releaseビルド、配布物確認で行う。実ゲームの起動・プレイ・性能測定は今回の実装工程から除外する。

## 調査結果と実装範囲

1.7.5011の公開APIは既存プロジェクトと同じ [Krafs.Rimworld.Ref 1.7.5011-unstable](https://www.nuget.org/packages/Krafs.Rimworld.Ref/1.7.5011-unstable) の参照DLLで確認した。メソッド内部の挙動には [1.7.4985 rev1269の公開逆コンパイル資料](https://github.com/codexvn/RimWorldDecompiled/tree/d5cbe1186bbb9962b7bd4913c900441c6fe4a4ff) を併用した。参照DLLが示すのは型とメソッドの利用可否であり、ゲーム内の動作や性能の確認は別工程とする。

| 候補 | リソースと使い道 | 確認したAPIと方針 |
| --- | --- | --- |
| 本拠点と遠征先の比較表示 | CPUでセルを集計し、RAMに最大2マップの結果を保持する。屋根、肥沃度、明るさをゲーム内で確認する | `Map.cellIndices`、`FogGrid.IsFogged`、`RoofGrid.Roofed`、`FertilityGrid.FertilityAt`、`GlowGrid.GroundGlowAt`。メインスレッドで必要な値を区切って複製する |
| マップの区画分析 | CPUで移動可能セルの連結区画、屋根の割合、肥沃な面積、暗いセルの集中箇所を算出する。RAMに結果を保持する | `GenGrid.Walkable` から得た値に対して、独立した4近傍探索・近傍集計を行う。結果は地図の可視化に使う |
| 物資の複数マップ集計 | CPUで品目・個数を集計し、RAMに検索用スナップショットを保持する。本拠点と遠征先の差が見える | `ListerThings.AllThings`、`Thing.def`、`Thing.stackCount`、位置・霧の判定。表示対象はマップ上の既知セルにあるアイテム |
| 生成したマップ画像のGPU描画・拡大 | ゲーム状態から作った画像をGPUへ転送し、VRAMに保持する。任意のGPU拡大処理を追加する | 参照DLLで `Texture2D.SetPixels32`、`Apply`、`GUI.DrawTexture`、`RenderTexture`、`Graphics.Blit` を確認。1.7.4985資料ではBlitがWaylithのGPU転送経路を使う |
| 生成マップのGPU並列計算 | GPUで近傍集計と色付けを行い、結果を既存のマップ画面に表示する | Waylithの `ComputeKernelCache.Load`、`ComputeDispatch.Rent`、`SetStorageImage`、`ComputeDispatchQueue.Enqueue` は1.7.5011参照DLLに存在。画像の利用・解放まで静的に追える場合にGPU計算経路を実装する |
| ロード予定のセーブの先読み | ストレージとRAMを使って指定した `.rws` 1本をOSキャッシュに読み込む | `GenFilePaths.FilePathForSavedGame` と `GameDataSaveLoader.LoadGame` を確認。まず既存のWindowsランチャーの明示オプションから、プロセス起動前に読み取る |

`UnityEngine.ComputeShader.Dispatch` は参照DLLには存在するが、1.7.4985版の互換層ではスタブだった。ネイティブGPU計算を組む際は、結果の利用まで追えるWaylithのAPIを使用する。近傍探索・集計・画像生成のCPU実装を共通の参照結果とする。ランタイムのパフォーマンスが未計測であることは、実装を止める理由にしない。

## 共通の設計

- マップの取得・描画・GPU操作をゲームスレッドに限定する。ワーカーが受け取るのは列挙済みの数値・ID・値配列。スナップショットはマップID、世代、観測区間を持ち、完了時に現在の世代と一致したものだけ表示する。
- 地図の表示と更新を設定で個別に選べるようにする。通常プレイ中は利用者が開いた画面の計算を先に処理し、ポーズ中は同時に可視化する最大2マップ分を作る。既存ワーカープールを使用し、セーブ、手動停止、空きRAM不足、フレームガード、外部並列処理に応じた上限を尊重する。
- 追加分のRAM、CPU処理数、GPU転送・生成件数、VRAM予約見積りを状態欄に出す。RAMは保持中・処理中の実バイト数を数え、ユーザーが閉じたマップ・モードで使ったデータから退避する。GPUは実ドライバー予算とアップロード見積りを既存のガードに通す。
- 霧のセルは集計・画像から除外する。マップ削除、ゲーム終了、MOD無効化で所有データを解放する。新機能は個別に初期OFFとし、資源を追加で使いたい利用者が選択する。実装・配布の完了判定は有用性の計測と分ける。
- 既存のTick、経路探索、予約、ガス、セーブ書き込みはゲーム本体と3 MODが担当する。可視化の結果を独自のゲーム状態としてセーブに入れない。

## タスク1　マップ取得とCPU/RAM分析

**主な接続先**

`Source/Game/ResourceRuntime.cs`、`Source/Core/ResourceController.cs`、`Source/Game/MoreUseResourcesMod.cs`。新規のゲーム側マップ集約とCoreの集計を分ける。パッチより既存のフレーム更新とゲーム内ウィンドウを優先する。

- [ ] 小マップの固定入力で、屋根セル数、肥沃度の範囲別面積、照度別面積、霧セルの除外、4近傍の連結区画、マップ削除と世代ずれを単体テストする。
- [ ] 複製するのは使用中レイヤーの値だけとする。1フレーム当たり最大1024セルを初期上限とし、既存フレームガードでも止める。セル数・世代を確認し、複数フレームの取得結果に観測区間を持たせる。
- [ ] CPUワーカーで集計とRGBA8生成を実行する。連結区画の基準はスナップショット取得時の歩行可否と4近傍とし、ドア、陣営、Pawnの動作、実ルート時間を判定対象に含めない。表示はエリアの概算として説明する。
- [ ] 最大2マップで指定したレイヤーと要約を保持する。各辺512ピクセル・集計系のRAM 64 MiBを初期上限とし、元マップが大きいときは表示を縮小する。配列の実サイズと処理中の予約を両方計上し、上限を超える取得はより粗い入力に縮小するか保留する。
- [ ] 単体テストとゲーム側のReleaseビルドで、Coreからゲーム型を参照していないこと、外部MODが欠落していてもビルド可能なことを確認する。

## タスク2　マップごとの物資集計

- [ ] 単体テストで、品目ID別の合計、霧・非表示対象の除外、同じセルに複数のスタックがある場合、マップID間の分離、同時にマップを切り替えた場合の旧結果棄却を確認する。
- [ ] `ListerThings.AllThings` の値をゲームスレッドで区切って読む。列挙中にリストを変更された場合は、その世代を破棄して負荷が落ち着いた時に再取得する。値の確定後はワーカーがID・個数を集計し、表示側が名称へ変換する。
- [ ] 同じ比較画面で両マップの品目と個数を検索できるようにする。取得直後の値と現在値の差を利用者が判断できるよう、観測時刻を表示する。タスク1と共有する世代判定・RAM予算・仕事枠を使う。

## タスク3　GPUによる生成マップの表示と拡大

- [ ] 純粋ロジックを単体テストする。RGBAバイト長、向きの四隅、最大512ピクセルの元画像から最大1024ピクセルの2倍描画、予算不足時の基本表示、世代切替時の旧GPUリソース破棄を確認する。
- [ ] 生成されたRGBAを `Texture2D.SetPixels32` と `Apply` でゲームスレッドから転送し、ゲーム内ウィンドウから `GUI.DrawTexture` で表示する。GPU更新は変更されたレイヤーのみとし、転送を同一フレームにまとめず既存フレーム予算内で分割する。
- [ ] GPU拡大を選んだ場合は形式とサイズを確認した単一の `RenderTexture` に `Graphics.Blit` する。既存の描画ターゲットを保存し、処理完了・失敗の双方で元に戻す。RenderTextureの実体が作れない場合とVulkan予算が不足する場合は生成元画像を使う。
- [ ] マップごとに現在のレイヤーの画像だけを保持し、置き換え・終了時にMod所有の `Texture2D` と `RenderTexture` をゲームスレッドで解放する。ドライバー予算の取得不能時は追加の拡大を保留する。ゲーム側のReleaseビルドで各呼び出しを照合する。

## タスク4　WaylithネイティブGPU計算

- [ ] 1.7.5011の参照と利用可能な実装資料から、GLSLを既存キューへ登録し、書き込み可能な出力を描画へ渡し、GPUが参照を終えた後に解放するまでの契約を列挙する。記録する項目は解決済み型、画像の用途フラグ、描画との順序、キャンセルと解放時点。Unity互換の `ComputeShader.Dispatch` の呼び出し成功だけでは完成とみなさない。
- [ ] 契約を満たせる場合は、近傍セルの照度・肥沃度を集計して色付けするGLSLカーネルを追加する。出力をタスク3の画面で読む。CPU参照結果のテストには小さい矩形と端・霧を含め、シェーダーにも同じ透明セルと境界処理を使う。
- [ ] MOD所有のストレージバッファ・画像に限定し、1世代1ジョブ、フレーム予算・VRAM予算・マップ寿命を共有する。既存Waylithキューを使い、メインスレッドで同期完了待ちをせずに描画へ渡す。構成が成立しない版・予算不足では、タスク3のGPU描画とCPU計算を使う。
- [ ] GPU出力の順序や寿命を1.7.5011の静的資料で確定できない場合は、満たせなかった具体的なAPI契約を記録する。GPUによる画像描画と拡大はタスク3で実装する。実行時の性能が未知でも契約が成立する機能は実装対象とする。

## タスク5　選択セーブの起動前先読み

- [ ] `tools/Start-RimWorldGc.ps1` に明示の `-WarmSaveFile` を追加する。単一の実在する `.rws` を読み取り専用で、最大256 MiB・5秒を初期予算としてOSキャッシュに載せる。パック先読みの有無と独立して有効にでき、両方使う場合も全体の予算を表示する。空きRAMに既存の6 GiB相当の余裕を残し、取得できない場合は先読みを省略して通常起動する。
- [ ] テスト用の一時ファイルで、指定なし、正常ファイル、予算超過、消失、読み取り失敗を確認する。PowerShellでの構文・対象関数の検証までを完了条件とし、実際のゲーム実行ファイルは起動しない。
- [ ] 先読み済みMiBと時間を表示し、起動時の使い方をREADMEへ追記する。ロード確定後に内部ローダーに近いタイミングで行う先読みは追加候補とし、ロードを待たせる同期I/Oは組み込まない。

## 完了条件

本計画と併用計画の純粋ロジック・異常系をテストし、ゲーム側Releaseビルド、同梱DLL一致、パッケージ内容、設定キーの日英対応を確認する。描画・GPU計算用のシェーダーを追加した場合はパッケージへの同梱とコンパイル可能性も確認する。実際のCPU・GPU使用率、見え方、速度改善、4 MOD併用時のゲーム内動作はこの完了判定に含めない。
