# Linux ベンチマーク（ゲームなし）の設計

対象: PR #5（ブランチ `claude/project-thread-8c4csj`）。実行は `tools/benchmark/run-benchmark.sh`（開発用のクラウド環境で行う。2026-11-20 に VM での実行はやめた）。

## 目的と方針

MOD が CPU・RAM・I/O をどれだけ効率よく使うかを、ゲームのない Linux 環境で繰り返し測れるようにする。

- 合成負荷ではなく、配布 DLL と同じ `Source/Core` のコード（`AssetAudit`、`FileCache`、`MappedPackResidency`、`WorkerPool`、`MemoryGovernor`、`ResourceController` など）を直接呼ぶ。ベンチマーク側は呼び出し方（コントローラと同じ Pump 間隔・同時実行上限・設定値）を再現し、時間と資源を測るだけにする。
- 本番コードは変更しない。変更は `MoreUseResources.Core.dll` への `InternalsVisibleTo`（テスト用 Core DLL にだけ入る）のみで、配布 DLL はバイト単位で同じことを CI と手元で確認した。
- ベンチマークは `Benchmarks/` の別プロジェクトで、`tools/package_mod.py` の配布 ZIP には入らない。
- 測れないもの（FPS・TPS・ゲーム内ロード時間・Windows 固有の I/O）は測らず、`analysis.md` と各シナリオの `NotReproduced` に明記する。

## 1 試行の流れ

1. シナリオが条件ごとの試行を作り、`Prepare` で部品（ワーカープール、ストア、コントローラ）を用意する。
2. 要求したキャッシュ状態を作る。warm は対象を読んでから `mincore` で常駐率を確認する。cold は対象を `posix_fadvise(DONTNEED)` で追い出す（root なら `drop_caches` も選べる）。確認できなければその試行を理由付きで集計から外す。
3. 全 GC の後、`/proc/self/status`・`io`・`stat`・スレッドごとの `stat`/`schedstat`/`status`、`/proc/stat`、PSI、ファイル記述子、GC 情報、ロック競合数、JIT 情報を取ってから `Execute` を測る。並行してサンプラーが RSS（匿名・ファイル）とネイティブ保持量のピークを取る。
4. 終了後に同じ値を取り直して差分を出す。MOD のスレッド（名前が `MUR-`）の CPU 時間を別に集計する。試行の中で生まれて消えるスレッドは前後の値から見えないため、終了時に `MUR-` スレッドが 1 本もないか、途中で消えたものがあれば 0 ではなく欠測にする。コントローラのようにスレッドが試行の中で始まって止まるシナリオは、開始直前と停止直前に自分で取る。GC 停止はランタイムのイベントから 1 回ごとの長さを取り、最大値と P95 を出す。
5. 後始末の後、3 秒以内に消えない `MUR-` スレッドと、試行中に開いたまま残ったファイル（ランタイムが初回に開くパイプ・DLL などは別に数える）を記録する。
6. 条件の実行順はラウンドごとにシード付きで並べ替え、時間による偏り（温度、他テナント）が特定の条件に集まらないようにする。ウォームアップのラウンドは集計しない。
7. ウォームアップのラウンドの後、JIT が 300 ms 続けて新しいメソッドをコンパイルしなくなるまで（最大 5 秒）待ってから測る。.NET の段階コンパイルは、よく呼ばれたメソッドを約 100 ms 後に別スレッドで再コンパイルするため、待たないと短いシナリオの最初の測定にその時間が入る。それでも JIT の時間が経過時間の 5% 以上になった試行は、`analysis.md` の「データの有効性」に件数を出す。

Pump の呼び方は 2 通りある。「cadence」はコントローラと同じ 250 ms ごと。「saturated」は同時実行上限（ワーカー × 2）だけが投入量を決めるようにして、作業自体の処理能力を測る。Pump を呼ぶジョブをプールの待ち行列の最後に入れ、そのジョブが Pump を呼んでから自分をもう一度最後に入れる。待ち行列は先入れ先出しなので、このジョブはワーカーが前のジョブを取り終えた直後に動き、タイマーにも余分なスレッドにも頼らない。Pump の呼び出しは重ならないようにし、待ち行列に何も残らなかったら連鎖を止めて、呼び出し側のスレッドが 1 ms ごとの確認と Pump を引き継ぐ。Pump 用のジョブ（数 µs）はワーカーの稼働時間には入るが、完了ジョブ数からは除く。

saturated は 2 回作り直した。最初は 1 ms ごとに呼んでいたが、小さいファイルでは 同時実行上限 × 約 900 回/秒（`Thread.Sleep(1)` の実際の間隔）で頭打ちになり、作業の能力ではなく呼び出し間隔を測っていた（R2 の実データで、1 ワーカー 1,770 items/s・稼働率 23%）。次にジョブの完了を待って回る駆動スレッドに替えたところ、そのスレッドが 1 コアを使い、ワーカー数が vCPU 数に達すると実行待ちが 64〜114% になってワーカーと CPU を奪い合った。今の方式はどちらの影響も持たない。

1 周の終わりの検出も経過時間に入るため、短い試行では確認の間隔が誤差になる。saturated では、連鎖が止まった（残りのジョブだけになった）時点で呼び出し側のスレッドを起こし、その後 2 ms は細かく確認してから 1 ms ごとに戻る。scan は最後のジョブがイベントを立てる。以前はそれぞれ 1 ms・5 ms ごとの確認で、smoke の数十 ms の試行では経過時間が数% 長く出ていた。

cadence 条件は、完走まで待つと長すぎるため `--rate-window-s` で打ち切り、速度と「この速度で 1 周に要する時間」（`projected_pass_s`）を記録する。打ち切った試行の完了時間は集計しない。

## シナリオ

| ID | 呼ぶ本番コード | 条件 | 主な測定値 |
|---|---|---|---|
| baseline | なし（計測基盤）、`WorkerPool` | 計測だけ / 待機中のプール × ワーカー数 | 計測自体の CPU とメモリ、待機中のワーカーの CPU |
| audit | `AssetAudit`（SHA-256、重複、`XmlManifestScanner`、`TextureAssetInspector`） | ワーカー数 × {cadence 250 ms, saturated（待ち行列が空くたび）} × {cold, warm}、2 周目の再走査 | items/s、MiB/s、CPU 並列度、ワーカー稼働率、読み取り増幅、結果ハッシュ |
| scan | `XmlManifestScanner.Scan`、`TextureAssetInspector.Inspect` | {xml, texture} × ワーカー数 × キャッシュ | 1 件あたりの CPU と確保量 |
| discovery | `GameAssetFiles.Discover`、`EnginePackFiles.Discover` | {アセット, パック} × メタデータ {warm, cold（root）} | 1 回の探索時間 |
| prefetch | `FileCache`（OS キャッシュのみ、パック優先） | ワーカー数 × {cadence, saturated} × キャッシュ、定期リフレッシュ | items/s、試行後の常駐率 |
| ram-hold | `FileCache`（RAM コピー保持） | {なし, OS 先読み, コピー保持, コピー保持＋OS キャッシュ追い出し}、すべて cold から | 後続の単一スレッド読み込みの時間とストレージ読み取り量、匿名メモリ |
| mapped-pack | `MappedPackResidency` | 上限 {なし, 半分, 全体} × キャッシュ | 常駐の準備時間、ランダム読み取りの時間、RssFile、縮小と解放 |
| controller | `ResourceController` 全体 | ワーカー数 × プリセット × キャッシュ、他MOD稼働通知の有無 | 探索・先読み・索引化・パック常駐の完了までの時間、ワーカー上限、停止時間 |
| cancel-resume | `WorkerPool`、`AssetAudit`、コントローラ | 一時停止、ワーカー数変更、`CancelJobs`、手動一時停止、設定変更 | 止まるまでの時間、停止中の進捗と読み取り、再開時間、取りこぼし |
| memory-pressure | `MemoryGovernor`、`ResourceController` | 対象 {コピー, パック} | 解放までの時間、不足中の読み取り、OS に戻った RSS、回復時間 |
| io-faults | `AssetAudit`、`FileCache`（保持あり） | {削除, 切り詰め, 書き換え, 改名, 権限, ディレクトリ置換, 混在} | 完走、停止、漏れた例外、エラー数、2 周目での内容変化の検出、削除ファイルのコピー残留 |
| xml-cache | `PatchedXmlStore`、`XmlDomCodec` | キャッシュファイル {cold, warm} | 保存と読み込みの時間 |
| lifecycle | `ResourceController`、`WorkerPool` | 生成・開始・停止の繰り返し | 残ったスレッド、停止時間、1 回あたりの匿名 RSS・ヒープ・FD の増加（Theil–Sen 傾き） |
| soak | `ResourceController` | メインメニュー、ロード、プレイ、高速、一時停止、セーブ、手動停止、メモリ解放、保持切替、メモリ不足を繰り返し、一定間隔で作り直す | 全 GC 後の定点値の時系列とリーク判定、停滞の検出 |

ワーカー数が vCPU を超える条件は、コントローラには論理プロセッサ数を max(N, vCPU) として渡し、結果には過剰割当として印を付ける。他MOD（WOWGAG's Performance Patch、Axen's Performance Enhancements、Overclock）は稼働中という通知だけを与え、MOD がワーカー上限や作業量を下げないことを確かめる（外部MOD併用で上限を下げない決定のとおり）。

## 統計と判定

- 条件ごとに中央値、P05、P95、最小、最大、平均、標準偏差、CV、IQR を出す（分位点は numpy の既定と同じ type 7）。試行が 20 未満の P95 は参考値と明示する。
- ワーカー数の頭打ち: 中央値が +10% を超え、かつ全試行の範囲が重ならない大きいワーカー数がない最小の数。
- 律速要因（スケーリング表の列）: 各条件の計測値から付ける。CPU 律速は MOD スレッドの CPU 並列度がワーカー数（vCPU が少なければ vCPU 数）の 75% 以上。CPU 競合は、プロセスの実行待ち時間がワーカー 1 本あたり経過時間の 10% 以上。I/O 待ちは cold で、PSI の I/O 待ちが経過時間の 30% 以上、スレッド別 I/O 待ちが 1 本あたり 30% 以上、またはワーカーがジョブ中なのに CPU にいない時間（実行待ちを除く）が稼働時間の 20% 以上。先読みで 1 ファイルが読み取り量の半分以上を占め、稼働率が 70% 未満なら「最大のファイルを 1 ジョブで読む時間」（`FileCache` は 1 ファイルを 1 ジョブで読むため、ほかのワーカーは先に終わって待つ）。ロック競合は、Monitor の競合が 1,000 回/秒を超え、かつスケーリング効率が 0.85 未満のときだけ挙げる（競合数はプロセス全体の値で、多いだけでは速度を落とした証拠にならないため）。稼働率 50% 未満で他に当てはまらなければ「供給側律速」。
- 2 回の比較: 各 3 試行以上、差 3% 以上、範囲が完全に分離したときだけ「改善」「悪化」。5 試行ずつで完全に分離すると、順位検定の両側 p ≈ 0.008 に相当する。
- 長時間実行のリーク判定: 最初の 10% を除き、全 GC 後の定点値の Theil–Sen 傾きと、最初と最後の 5 分の 1 の中央値の差が、両方とも閾値を超えたら「疑い」。1 時間未満のデータでは「疑い」までにとどめる。閾値（1 時間あたりの傾き / 増加量）: 管理ヒープ 2 / 4 MiB、ネイティブを除く匿名 RSS 16 / 32 MiB、GC コミット 8 / 16 MiB、FD 1 / 8、MOD スレッド 0.5 / 2、全スレッド 1 / 4。
- 生成データでは、仕込んだ件数（XML、壊れた XML、Def、衝突、正常・壊れたテクスチャ、重複）と索引化の結果を照合する。

## 再現性と記録

- `metadata.json` にコミット SHA、ブランチ、未コミット変更の有無、VM（GCE のマシンタイプ・ゾーン・CPU プラットフォーム、CPU 名、vCPU、メモリ、カーネル、THP、cgroup の制限）、.NET と GC 設定・GC 関連の環境変数、全オプション、入力データの構成指紋（と任意で内容指紋）、開始日時を記録する。
- 結果ファイルのパスはデータの場所を `<data0>`、出力先を `<out>` などに置き換え、利用者のディレクトリ名を残さない。
- 生成データは決定的で、同じパラメータなら同じ指紋になる。R2 の実データは取得一覧の SHA-256 を `r2-dataset.json` に残す。

## 安全装置

プロセス RSS、マシンの空きメモリ、作業用ファイルの容量、ディスクの空き、総実行時間を 0.5 秒ごとに確認し、超えたら実行を止めてそれまでの結果と分析を残す。実行スクリプトは外側にも `timeout --signal=INT` を掛ける。

## CI

GitHub Actions は既存のジョブ（テスト、ビルド、配布 DLL の一致、パッケージ）に加え、ベンチマークの単体テストと、生成データ 16 MiB・ワーカー 1,2・試行 1 の短いスモークだけを実行し、結果を成果物として保存する。長時間・高負荷・実データの実行は開発用のクラウド環境で手動で行う。

## 手元の短い実行で分かったこと

いずれも 4 vCPU・16 GiB のクラウドコンテナで、試行数の少ない smoke 設定の参考値（VM の測定ではない）。数値は R2 の smoke プロファイル（Core の公式データ、Assets.zip、Workshop の MOD 12 個）から選んだ 1,500 ファイル・14.7 MiB とパック 2 個、各条件 3 試行の中央値。本番コードの構造に由来する事実は、コードと測定の両方で確かめたものだけを挙げる。

1. コントローラの Pump 間隔が速度を決めている。索引化と先読みは 250 ms ごと（`SlowEvery` 5 × 50 ms）にしか新しいファイルを投入せず、同時実行上限は ワーカー数 × 2 なので、上限は ワーカー数 × 8 ファイル/秒になる。測定は索引化・先読みとも 1・2・4 ワーカーで 7.99・15.98・31.96 ファイル/秒で上限どおり、索引化のワーカー稼働率は 0.1〜0.3%。同じ処理を待ち行列が空くたびに投入すると、索引化は warm で 20,922・34,787・59,413 ファイル/秒（CPU 律速、MOD スレッドの CPU 並列度 0.97・1.94・3.44、稼働率 98〜100%）、cold で 9,223・17,808・27,680 ファイル/秒（I/O 待ち）出たので、250 ms 間隔の速度は処理能力の 0.04〜0.12%。既定の設定ではこの 4 vCPU でワーカー上限が 2 になり、コントローラ全体の索引化は 15.5 ファイル/秒だった。この速度なら R2 の all（44,998 ファイル）の 1 周は約 48 分かかる計算になる。ワーカー数を増やすより、投入の仕方が支配的。
   - 先読み（OS キャッシュのみ）は warm の 1 ワーカーで 26,315 ファイル/秒（CPU 律速）。2 ワーカー以上は稼働率が 32〜61% に下がり伸びない。`FileCache` は 1 ファイルを 1 ジョブで読むため、Assets.zip（338.8 MiB、読み取り量の 96%）を読む 1 本が終わるまで 1 周が終わらない。cold では 7,439・9,826・12,572 ファイル/秒（I/O 待ち）。
   - XML 解析とテクスチャ検査だけ（scan）は warm で XML 24,857・33,987・48,260、テクスチャ 30,510・52,502・85,111 ファイル/秒。4 ワーカーでは 4 vCPU を取り合い、実行待ちが 57〜92% になった。
   - ベンチマークの不備として、saturated を当初は 1 ms ごとに呼んでいた。この方式では同時実行上限 × 約 900 回/秒で頭打ちになり（1 ワーカー 1,770 ファイル/秒、稼働率 23%）、作業の能力を測れていなかった。2 回作り直した経緯は「1 試行の流れ」の後の段落を参照。
2. 索引化は XML と PNG/DDS を 2 回開いて読む（ハッシュ用と検査用）。生成データで読み取り量は対象の 1.85 倍だった。
3. XML 検査の見落とし: `XmlManifestScanner` は Def の `defName` を読むと `ReadSubtree` を途中で閉じる。残りを読み飛ばす途中の構文エラーで外側のリーダーが `ReadState.Error` になっても `Read()` が false を返すだけで、壊れた XML を正常と数え、その Def も数える。defName より前で途切れたファイルは正しく検出する。影響は MOD の状態表示の統計だけ。テスト `XmlScannerKnownGapTests` に現状の挙動を記録した（修正は別変更）。
4. 削除・改名されたファイルの RAM コピーが残る。`FileCache` は開けなくなったファイルを訪問済みとして扱い、定期リフレッシュでもコピーを解放しない（I/O 障害の測定で 22 件・4.5 MiB）。コントローラではファイル一覧の再探索で変化が見つかると全コピーを解放して読み直すので、それまで残る。
5. `WorkerPool.CancelJobs` は待機中のジョブを捨てるため、`AssetAudit` の実行中カウントが減らず、その後は完了しない。現行 MOD では `Dispose` からしか呼ばれないので実害はない。
6. 手動一時停止中、待機中のジョブはキューに残り、再開時に実行される（停止中の読み取りは 0.02 MiB 未満）。
7. `RamHoldCopies` の切り替えや、パック常駐上限をマップ済みの量より下げる変更は、保持を全部解放して最初からやり直す。パックは一部ではなく丸ごと常駐の対象外になるので、上限がパックより小さいと常駐は 0 になる（R2 の Assets.zip は 338.8 MiB、既定の上限 2,048 MiB には収まる）。
8. メモリ不足の通知から 0.15〜0.25 秒で保持を解放し、不足の間は読み取りを始めない。解放したネイティブコピーが匿名 RSS として OS に戻る量は試行ごとに 0〜11 MiB（保持 14 MiB）とばらつき、`malloc_trim` の後は戻った。glibc の malloc が解放済みの領域を抱えるためで、Windows のヒープでは別の挙動になる。
9. 他MODの稼働を通知しても、ワーカー上限と最大稼働数は通知なしと同じだった。
