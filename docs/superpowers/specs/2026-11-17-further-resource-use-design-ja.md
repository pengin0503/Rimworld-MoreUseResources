# 追加の資源活用と設定の拡充　設計書（2026-11-17）

状態: **設計のみ。実装はまだ行いません。** 依頼者の指示（2026-11-17）により、設計をリポジトリに保存するところまでを範囲とします。

対象: RimWorld Windows 1.7.5011 rev24 / .NET 10 / Waylith。根拠は[調査書](../../plans/2026-11-17-further-resource-use-survey-ja.md)と[静的検証の記録](../../review/2026-11-17-external-mod-coexistence-ja.md)です。実機での計測はしていません。

## 変わらない原則

- 外部MODの稼働や共有ジョブプールの混雑を理由に、本MODのワーカー上限と処理量を下げません。
- 本体が実際に消費している処理だけを前倒し・保持・増枠します。合成負荷や新しい集計は足しません。
- 他MODの設定は、ゲーム内からも通常起動からも書き換えません。
- 新しい項目は、すべて設定画面でON／OFFと数値の調整ができるようにします。初期値は「現在の動作と同じ」にし、更新しただけで挙動が変わらないようにします。

## 1. GCの第0世代の予算（RAM）

起動スクリプトに引数を1つ足します。ゲーム内の設定ではなくスクリプトの引数にする理由は、GCの構成がプロセス開始時にしか読まれないためです。

| 項目 | 内容 |
| --- | --- |
| 引数 | `-GcGen0SizeMiB <整数>`。省略時は何も設定しません（現在と同じ動作）。 |
| 範囲 | 0（設定しない）、または 16〜4096。範囲外は起動前にエラーにします。 |
| 動作 | 起動するゲームプロセスの環境変数 `DOTNET_GCgen0size` と `COMPlus_GCgen0size` に、バイト数を16進で設定します。既存の `-Profile` と同じく、親プロセスや恒久設定には触れません。 |
| `-Profile Default` との関係 | `Default` はGC関連の変数を何も設定しない指定です。`-GcGen0SizeMiB` を同時に指定した場合は、この1つだけを設定し、その旨を表示します。 |
| 空きRAMの確認 | 既存の `-WarmMinFreeMiB` と同じ取得方法で空き物理RAMを読み、「予算×ヒープ数の見込み」が空きの半分を超える場合は警告を出して設定しません。Serverプロファイルではヒープ数が論理CPU数になり得るため、`-ServerHeapCount` の指定があればその数、なければ論理CPU数で見積もります。 |
| 表示 | 設定した値を起動時に1行で表示します。ゲーム内の状態欄には、既存のGC表示の横に「第0世代の予算（起動時の指定値）」を出します。表示するのは自プロセスの環境変数の値で、GCが実際に採用した値ではありません。変数がなければ「指定なし」と表示します。 |

**実装前に確かめること（判定条件）**

- WaylithのカスタムCLR（`10.0.15-waylithclr.dev`）がこの変数を読むかは静的に確定できません。実機で、同じセーブ・同じ速度の10秒窓を、指定なしと指定ありで比べます。第0世代のGC回数が減らなければ「効かない設定」として引数を削除します。
- 第0世代を広げると1回あたりの停止時間が延びることがあります。回数だけでなく、状態欄の停止時間の合計と最大も比べます。

**テスト**: 既存の `tools/Test-StartRimWorldGc.ps1` に、省略時は変数を設定しないこと、16進の値、範囲外の拒否、`Default` との併用、空きRAM不足時に設定しないことを追加します。起動する代わりに、設定予定の環境変数を出力する確認用の引数（`-NoLaunch` 時に一覧を表示）を使います。

## 2. Vulkanパイプラインキャッシュの引き継ぎ（ディスク、RAM、CPU）

### 確認済みの事実

- `Waylith.Rendering.MeshPipelineCache` は、生成時に空の `VkPipelineCache` を作ります。ディスクへの保存はありません。
- `MeshPipelineCache` は `MeshBatchRenderer` ごとに1つあります。`MeshBatchRenderer` はカメラのスロットごと、レンダーテクスチャ描画ごとに作られるため、**キャッシュは複数あります**。
- エンジンのVulkanバインディング（`Brutal.Vulkan.dll`）に、公開メソッド `GetPipelineCacheData_Count`、`GetPipelineCacheData_Write`、`MergePipelineCaches`、`CreatePipelineCache` があります（R2の Game-Windows から取得して確認）。
- 描画は専用のレンダースレッド（`Waylith.Rendering.RenderThread`）で進みます。
- `pipelineCache` フィールド、`MeshBatchRenderer.pipelines` フィールドはprivateです。

### 設計

| 項目 | 内容 |
| --- | --- |
| 設定 | 「パイプラインキャッシュを次回起動へ引き継ぐ（実験機能）」ON／OFF、初期OFF。「保存の上限（MiB）」8〜256、初期64。「保存の間隔（分）」0〜60、初期10（0は終了時のみ）。 |
| 保存 | 各キャッシュから `GetPipelineCacheData` で内容を取り出し、1つのファイル `MoreUseResources-PipelineCache.bin` にまとめます。ユーザーデータフォルダに、一時ファイルと置換で書きます。取り出しはVulkanの仕様上、外部の同期を必要としません。 |
| 復元 | 起動後、保存した内容から一時的なキャッシュを作り、エンジンの各キャッシュへ `MergePipelineCaches` で併合してから一時キャッシュを破棄します。エンジンのキャッシュは置き換えません。 |
| 照合 | ファイルの先頭に、形式番号、本体ビルド、GPUのベンダーID・デバイスID・ドライバーバージョン・`pipelineCacheUUID`、内容のSHA-256を置きます。1つでも一致しなければ使いません。Vulkanのキャッシュ自体のヘッダーもドライバーが検査します。 |
| 上限 | 上限を超える内容は保存しません。読み込み時も上限を超えるファイルは使いません。 |
| 停止条件 | 反射で到達できない、関数が例外を返す、照合に失敗する、のいずれかで、その起動中は機能を止め、状態欄に理由を1行で表示します。 |
| 表示 | 復元したバイト数、併合したキャッシュの数、保存回数、最後の保存サイズ。 |

### 実装前に確かめること（判定条件）

これらが満たせない場合、この項目は実装しません。

1. **併合の同期**。Vulkanの仕様では、併合先のキャッシュは外部で同期する必要があります。レンダースレッドがパイプラインを作っている最中に併合してはいけません。レンダースレッドが確実に止まっている時点（フレームの提出と提出の間など）を公開APIで得られるかを、`RenderThread` と `FrameRenderer` を読んで確定させます。privateな待機オブジェクトに頼る方法は採りません。
2. **到達経路**。すべての `MeshBatchRenderer` を列挙できる経路があるか（`MeshBatchRenderer.ReloadAllShaders` が静的に全件を扱っているため、静的な登録簿がある見込みです）。
3. **効果の有無**。AMDとNVIDIAのドライバーは独自のディスクキャッシュを持ちます。実機で、起動直後に初めてマップを表示したときのフレーム時間を、OFFとONで比べます。差が計測誤差の範囲なら採用しません。
4. **対象外**。ポストエフェクトとコンピュートのパイプラインはキャッシュなしで作られており、この方法では扱えません。

**テスト**: ファイル形式の読み書き、照合の各不一致、破損、上限超過、置換の失敗を、ゲームに依存しないCore側の単体テストにします。Vulkanの呼び出しそのものは単体テストにできないため、静的照合と実機確認の対象とします。

## 3. 既存機能の上限の引き上げ（CPU、VRAM）

いずれも現在は固定値です。設定項目にし、初期値を現在の固定値と同じにします。

| 機能 | 現在の固定値 | 設定項目（範囲、初期値） |
| --- | --- | --- |
| JIT先行コンパイル | 最大8,000メソッド、1アセンブリ最大1,024、ワーカー最大2 | メソッド上限 1,000〜200,000（初期8,000）。アセンブリごとの上限 256〜16,384（初期1,024）。ワーカー上限 1〜本MODのワーカー上限（初期2）。 |
| GPU先読みの1フレームの量 | 候補48件、アップロード4件 | アップロード 1〜32（初期4）。候補はアップロード数の12倍で連動。 |
| GPU先読みの保留件数 | 2,048件 | 256〜16,384（初期2,048）。 |
| GPU先読みの画像サイズ | 1,024〜4,096px（既存の設定） | 変更なし。プリセットが設定する値を2,048から「VRAMが12 GiB以上なら4,096、それ未満は2,048」に変えます。 |
| グラフィック事前構築の1フレームの量 | 候補12件 | 1〜64（初期12）。 |
| 画面外区画の先行更新 | ポーズ中のみ、1フレーム1区画、1回に64区画まで確認 | 動かすフェーズ: ポーズ中のみ／ポーズ中と通常速度／ポーズ中と通常速度と高速（初期はポーズ中のみ）。1フレームの区画数 1〜4（初期1）。 |
| テクスチャ需要履歴 | 512件、1 MiB、保存間隔60秒 | 件数 64〜4,096（初期512）。保存間隔 30〜600秒（初期60）。ファイル上限は件数に比例させ、最大8 MiB。 |
| シェーダーキャッシュの先読み | 4,096件 | 256〜16,384（初期4,096）。 |

- JITのワーカー上限を上げても、本MODのワーカー上限、フェーズ設定、適応制御、フレームガードの範囲を超えません。WOWGAGのJIT準備が有効なときは、従来どおりその作業単位を譲ります。
- 区画の先行更新を通常速度で動かす場合も、フレームガードが働いている間は動かしません。WOWGAGが区画更新を置き換えている構成では、従来どおり譲ります。
- 上限を上げる項目には、設定画面で「フレーム時間が伸びることがあります」と注記します。

**テスト**: 各項目の範囲の丸め（`Normalize`）、初期値が現在の固定値と一致すること、プリセット適用後の値、上限に達したときに止まることを単体テストにします。

## 4. すべての処理を設定でON／OFFできるようにする

現在、独立したスイッチを持たない処理が残っています。それぞれにスイッチを足します。初期値は現在の動作と同じです。

| 処理 | 現在 | 追加する設定（初期値） |
| --- | --- | --- |
| コンパイル済みシェーダーの先読み | OS先読みがONなら常に動く | 「シェーダーキャッシュを先読み」ON |
| エンジンのパック（テクスチャキャッシュZIP、Assets.zip）の先読み | OS先読みがONなら常に動く | 「エンジンのパックを先読み」ON |
| コピー予算が足りないファイルのOS先読み | 常に動く | 「コピー予算待ちの間もOSキャッシュへ読む」ON |
| テクスチャ需要履歴の保存と次回の優先 | 需要優先がONなら常に動く | 「需要履歴を次回起動へ引き継ぐ」ON。OFFにしてもファイルは消しません。別に「履歴を消去」ボタンを置きます。 |
| GCの計測表示 | 常に動く | 「GCの計測を表示」ON |
| 他MODの状態表示 | 他MODがあれば常に表示 | 「他のパフォーマンスMODの状態を表示」ON |
| 作業単位の譲渡 | 重複を検出すれば常に譲る | 単位ごとに「他MODが同じ処理を置き換えていても実行する」OFF。ONにすると二重実行になるため、設定画面に警告を出します。XMLの2工程とXMLパッチキャッシュは起動時に決まるため、再起動後に反映と注記します。 |
| Overclockの構成に関する通知（下記5） | なし | 「Overclockの並列設定が効かない構成を通知する」ON |

設定画面の構成は、項目が増えるため次のようにします。

- 資源ごと（全般、CPU、RAM、GPU、他MOD）の見出しは現在のまま使い、各見出しの中を「基本」と「詳細（上限と間隔）」に分けます。詳細は折りたたみ、初期状態は閉じます。
- 各スイッチの横に、その処理が今動いているか、止まっているならその理由（フェーズ、予算、譲渡、非対応ビルド）を短く表示します。状態欄の既存の行を、対応するスイッチの近くへ移します。
- 「初期値に戻す」を見出しごとに置きます。
- 文言は日本語と英語の両方に追加し、キーと差し込み位置の一致は既存のパッケージ検査で確認します。

## 5. Overclockの並列Pawn Tickが適用されない構成の通知

### 根拠（配布DLLで確認）

- Overclockの並列Pawn Tick（最適化ID `parallelPawnTicks`、初期OFF）は、WOWGAGが有効で、その設定 `parPawnTick`、`parPawnComps`、`parWork`、`parPredictConst`、`parPredictFail`、`parPredictJob`、`parMapPost` のいずれかがONのとき、適用されません（`ParallelPawnTicks.ForeignThreadingOn`）。
- 適用されなければワーカープールは起動しないため、`parallelThreads` を変えても効果がありません。
- Overclockは、適用しなかった理由を `Optimisation.FailureReason`（公開プロパティ）に入れます。

### 通知を出す条件

次のすべてを満たすとき、1回の起動につき1回だけ出します。

1. 「Overclockの並列設定が効かない構成を通知する」がON。
2. Overclock（`soap.overclock`）とWOWGAG（`wowgag.guiperformancepatch`）がどちらも有効。
3. Overclockの設定で `parallelPawnTicks` がON（`OverclockSettings.optimisations` の値。項目がなければ初期値のOFFとして扱う）。
4. Overclockの `ParallelPawnTicks` が稼働していない（`Active` が偽）。
5. WOWGAGの上記7項目のいずれかがON。

判定はロード完了後、マップが表示されてから行います。Overclockは並列Pawn Tickの適用をロード完了後まで遅らせるため、それより前に判定すると誤って通知します。読み取れない値が1つでもあれば通知しません（推測で警告しません）。

### 通知の内容

- 形式は、ゲームの標準のダイアログ（`Dialog_MessageBox`）です。ボタンは「閉じる」と「2度と表示しない」の2つです。
- 本文（日本語）: 「Overclockの並列Pawn Tickは、WOWGAG's Performance Patchの並列設定（{ONになっている項目名}）がONのため適用されていません。この構成では、Overclockのワーカースレッド数（parallelThreads）を変えても効果がありません。どちらの並列処理を使うかは、各MODの設定画面で選んでください。」
- Overclockの `FailureReason` が読めた場合は、「Overclockの表示: {その文}」を補足として付けます。
- 「2度と表示しない」を押すと、本MODの設定 `OverclockIneffectiveNoticeDismissed` を真にして保存します。以後は条件を満たしても出しません。
- 設定画面に「通知を再び表示する」ボタンを置き、押すとこの値を偽に戻します。
- 通知とは別に、状態欄の他MODの欄には同じ内容を1行で常に表示します（状態表示のスイッチに従います）。ダイアログを消した後も、現在の構成を確認できるようにするためです。
- 本MODはどちらのMODの設定も変更しません。

**テスト**: 条件の判定をゲームに依存しない関数にし、5条件の組み合わせ、読み取り不能な値、「2度と表示しない」の後、再表示の後、同じ起動での2回目を単体テストにします。

Overclockの作者による計測の記述は、[参考MODの調査資料](../../research/2026-11-16-reference-performance-mods-ja.md)に追記しました。本設計の起動スクリプトの説明と通知の文面は、この記述と矛盾しないようにします。

## 実装の順序（着手する場合）

1. 設定の拡充（4）と上限の設定化（3）。挙動を変えない初期値で入るため、最初に入れて土台にします。
2. Overclockの通知（5）。
3. GCの第0世代の予算（1）。実機での判定が必要です。
4. パイプラインキャッシュ（2）。判定条件の1と2を静的に確定させてから着手し、満たせなければ見送ります。

各段階で、単体テスト、起動スクリプトの検証、Releaseビルド、同梱DLLの一致、配布ZIPの確認を行います。
