# PC での短い計測（数値を貼るだけ）

残っている判断（XML キャッシュなど）と、実機で未確認の 3 点（状態欄のパック個数、ロード工程の記録、GC の値）を、ゲームを 1 回起動して取ります。所要時間はゲームの起動を含めて約 15 分です。対象は Windows の RimWorld 1.7 です。

測った値は MOD 設定画面の「状態をコピー」ボタンで、まとめてクリップボードに入ります。同じ内容が `MoreUseResources-Status.txt` にも追記されます。手で書き写すものはありません。設定は今のままで構いません（コピーに全設定が入ります）。

後から別の判断が必要になっても測り直さずに済むよう、コピーには、ゲームとエンジンが追加の処理なしで読める値をまとめて入れています。CPU をどこで使っているか（ゲーム全体、メインスレッド、PC 全体、スレッドの種類別）、メインスレッドの時間のうちティック・マップ更新・UI の割合、JIT、ファイルの読み取り、ストレージ待ちのページフォールト、フレームの引っかかり、フレーム上限、起動からロード完了までの内訳、エンジン自身の RAM と VRAM の内訳です。計測そのものにかかった時間も入るので、計測がゲームを遅くしていないかも確かめられます。

## 1. MOD を入れる（初回だけ）

1. GitHub で次の ZIP をダウンロードします。
   `https://github.com/pengin0503/Rimworld-MoreUseResources/archive/refs/heads/main.zip`
2. 展開してできたフォルダの名前を `Rimworld-MoreUseResources` に変えます。
3. Steam のライブラリで RimWorld を右クリックし、「管理」→「ローカルファイルを閲覧」で開いた中の `Mods` フォルダに置きます。古い `Rimworld-MoreUseResources` があれば先に削除します（同じ MOD が 2 つあると読み込みが崩れます）。フォルダ名を同じにすると、MOD の設定は引き継がれます。

## 2. 1 回目（必須）

1. Steam からいつも通り起動し、タイトル画面まで待ちます。
2. いつものセーブをロードします。
3. ゲーム速度を 3（`>>>`）にして、合計 5 分以上プレイします。ポーズ中、メニューを開いている間、別のウィンドウに切り替えている間は数えないので、途中で止めたり Alt+Tab したりしても構いません。
4. Esc →「オプション」→ 左の「MODオプション」→「More Use Resources」（上の検索欄に `More` と入れると早く見つかります）を開き、一番上の **状態をコピー** を押します。
5. 画面左上に「クリップボードにコピーし…」と出たら、このスレッドに Ctrl+V で貼ります。
6. できれば `Player.log` も添付してください（場所は下の「うまくいかないとき」）。他の MOD のログとエラーも入っているので、後から必要になったときに測り直さずに済みます。

## 3. GC の種類

2026-11-20 の比較（下の結果）から、MOD 設定「Server GC でゲームを起動する」（初期 ON）が、ゲームの起動設定ファイル `RimWorld.runtimeconfig.json` に Server GC の指定を書くようにしました。Steam からの普通の起動でも Server GC になりますが、GC の種類は起動時に決まるので、効くのは書いた次の起動からです。**この版を入れた最初の起動は元の GC のまま**なので、比べるときは 1 度起動して終了してから測ります。

貼る前に、状態欄の `GC の種類：この起動は Server（起動設定ファイルの System.GC.Server=true による）` の行を見てください。`Workstation` のままでも、そのまま貼ってください（その行の「起動設定ファイル：」の後ろに、書けなかった理由が出ます）。

ファイルを書けなかったときだけ、次の方法でその起動を Server GC にできます。

1. ゲームを終了します。
2. 上の手順で開いたゲームのフォルダで、`RimWorld.exe` を Shift を押しながら右クリックし、「パスとしてコピー」を選びます。
3. スタートボタンを右クリック →「ターミナル」を開き、`$env:DOTNET_gcServer='1'; Start-Process ` と入力した後ろに Ctrl+V で貼って Enter を押します。（この MOD の `tools` フォルダーにある `Start-RimWorld-ServerGc.cmd` をダブルクリックしても同じ設定で起動します。こちらは Windows でまだ試していません。）

## うまくいかないとき

- **ボタンがない**：古い DLL が読み込まれています。`Mods` に同じ MOD が 2 つないか確認してください。
- **コピーできない、貼れない**：エクスプローラーのアドレス欄に `%USERPROFILE%\AppData\LocalLow\Ludeon Studios\RimWorld by Ludeon Studios` と入力して開き、`MoreUseResources-Status.txt` をスレッドに添付してください。ボタンを押すたびに、その時点の内容が後ろに追加されます（1 MiB を超えると作り直します）。`Player.log`（同じ場所の `Logs` フォルダー）にも `[More Use Resources] Status snapshot:` として書きますが、2026-11-20 の 218 MOD の環境では、読み込み後のメッセージが警告以外 1 行も残っていませんでした（原因の MOD は未特定）。

## 2026-11-20 の結果と決めたこと

Windows 11、16 論理 CPU、RAM 32 GB、218 MOD、2560x1440、RimWorld 1.7.5014 rev1195。どちらも同じセーブで、速度 3（倍率 6）の区間だけを比べます。1 回ずつの比較です。

| | 1 回目（Workstation GC） | 2 回目（Server GC） |
| --- | --- | --- |
| 数えた時間 | 110 s（11 区間） | 280 s（28 区間） |
| TPS（目標 360） | 359.0（100%） | 359.6（100%） |
| FPS | 141.2 | 137.9 |
| GC の停止 | 1,260 ms（1.15%） | 395 ms（0.14%） |
| 最悪の 10 秒の GC 停止 | 179 ms | 73 ms |
| 50 ms を超えたフレーム | 4 回（1 分あたり 2.2 回） | 7 回（1 分あたり 1.5 回） |
| 100 ms を超えたフレーム、最長 | 2 回、181 ms | 1 回、116 ms |
| メインスレッド、PC 全体の CPU | 70%、12% | 78%、14% |
| メインスレッドの内訳（ティック、マップ更新、UI） | 25%、13%、11% | 26%、17%、12% |
| ハードページフォールト | 10.3 回/秒 | 0.0 回/秒 |
| 空き RAM の最小 | 15,912 MiB | 16,674 MiB |
| GC がコミットした最大 | 2,314 MiB | 2,429 MiB |
| 起動からロード完了、うち GC の停止 | 38.9 s、4.1 s | 35.3 s、1.3 s |

- **GC**：Server GC を勧めます。停止の割合は約 8 分の 1、最悪の 10 秒は約 4 割になり、ロード中の停止も 2.8 s 減りました。増えたメモリは約 115 MiB です。GC の種類はプロセスの中からは切り替えられないので、MOD 設定「Server GC でゲームを起動する」（初期 ON）がゲームの起動設定ファイルに書き、次の起動から Server GC にします（手順の 3）。1 回目は環境変数 `DOTNET_gcServer=1` と `DOTNET_GCHeapCount=8` がプロセスにあったのに Workstation でした。理由は分かっていません（R2 にある MOD 1,460 個の DLL に、GC の環境変数を書き込むものはありませんでした）。
- **CPU**：TPS は目標どおりで、メインスレッドにも PC 全体にも空きがあります。この場面では CPU を足しても速くなりません。
- **ストレージと RAM**：プレイ中のゲーム自身のファイル読み取りはほぼ 0 で（読み取りは全部この MOD の分）、2 回目のハードページフォールトは 0 回/秒、ロード完了までの合計も 14〜20 回でした。空き RAM が 15 GB 以上あるのでパックのページが追い出されることもなく、`Assets.zip` の RAM 常駐（`RamResidentPacks`）は効く場面がありません。1 回目の 10.3 回/秒は、この起動ではこの MOD の再先読み（1 回）と検査が動いていたので、その読み取りの分の可能性があります（未確認）。この 2 回はどちらもキャッシュが温まった起動なので、PC を再起動した直後の起動に先読みが効くかは分かりません。
- **JIT**：プレイ中の JIT は裏の `.NET Tiered Compilation Worker`（0.03〜0.05 コア）で、メインスレッドを止める分は分けて数えられません。先行コンパイルを試す根拠にはなりません。
- **GPU**：当時の MOD はビルド番号で対応版を絞っていたので、この版では GPU の機能も VRAM の値も止まっていました。今は 1.7 のすべてのビルドで動きます。VRAM はこれ以上測りません。
- **計測のコスト**：メインスレッドで 1 区間 6.8〜7.9 ms かかっていました。直したあとの値は次のコピーで確かめます。

## 貼られた値で決めること

| 見る値 | 決めること |
| --- | --- |
| 先読み対象のエンジン用テクスチャキャッシュ・アセットパックの個数 | 0 なら先読みの不具合として直します。1 以上なら、パックの先読みが実機で働いています。 |
| ロード工程の所要時間（`process start to mod`、XML の各工程、`peak working set`） | XML の工程が長ければ XML キャッシュを試す価値があります。`process start to mod`（テクスチャと音声の読み込み）が大半なら、テクスチャ側を優先します。 |
| プレイ中の平均の GC（停止の割合、最悪の 10 秒）と TPS、状態欄の「GC の種類」 | Server GC を既定にしたので、2026-11-20 の 2 回目（停止 0.14%、最悪の 10 秒 73 ms）と同じくらいかを確かめます。 |
| TPS と目標に対する割合（`TPS 300.0 (83% of 360)`。目標は 60 × 速度の倍率） | 100% 近くならゲームは指定の速度で回っていて、CPU を足しても速くなりません。下回っていれば、下の行でどこが詰まっているかを見ます。 |
| プレイ中のメインスレッドの使用率、ゲーム全体と PC 全体の CPU 使用率 | メインスレッドが 100% 近くで TPS が頭打ちなら、メインスレッドの仕事を減らす方向だけが効きます。PC 全体に空きがあれば、ほかのスレッドへ回せる仕事を探す価値があります。 |
| メインスレッドの時間の内訳（`main thread in ticks …, map update …, UI …`） | ティックが大半ならゲームの計算そのものが重く、この MOD のリソースでは速くなりません。マップ更新（地図の描画と、部屋・電力・光などの更新）が大きければ、描画側の仕事（区画の作り直しの前倒しなど）を調べる価値があります。UI が大きければ、UI を描く MOD を疑います。 |
| スレッド別の CPU（`CPU cores by thread: main …, RenderThread …, WaylithJob (15) …`。値は使っているコア数） | `RenderThread` が 1.00 近くなら描画スレッドが詰まっています。`main` も `RenderThread` も低いのに FPS がフレーム上限より低ければ、GPU 待ちの可能性が高いです（ハードページフォールトが多ければストレージ待ちです）。`WaylithJob` の合計がスレッド数より十分小さければ、エンジンのジョブには空きがあります。`MUR-` で始まるものはこの MOD の分です。 |
| ハードページフォールト（`hard page faults …/s`、起動中の合計） | ゲームがストレージからの読み込みを待った回数です。プレイ中にほぼ 0 なら、`Assets.zip` の RAM 常駐も先読みの強化も効きません。多いときは、空き RAM が少なければメモリ不足（ページファイル）、空きがあれば `Assets.zip` などメモリマップの読み込みなので、常駐を試す価値があります。 |
| フレーム上限（コピーの先頭の `frame cap`） | FPS が上限と同じなら、メインスレッドは待っている時間があり、FPS は上がりません。 |
| 計測にかかった時間（`measuring took … ms per window on the main thread …, reading threads … ms on a background thread …`） | 1 区間（10 秒）あたりの値です。メインスレッドの分が数 ms を超えていたら、計測を軽くします。スレッド一覧の読み取りは別スレッドで行うので、ゲームのフレームを止めません（その CPU 時間は `.NET TP Worker` に入ります）。 |
| プレイ中と起動中の JIT の時間 | 合計が大きければ JIT の先行コンパイルを試す価値があります。小さければ不要です。 |
| プレイ中の読み取り量（`I/O read`、括弧内の本 MOD 分を差し引いて見る）とパックの展開時間 | プレイ中もゲームがファイルを読んでいれば、OS キャッシュへの先読みを続ける意味があります。この量は OS キャッシュから返った分も含むので、ストレージまで行ったかはハードページフォールトと合わせて見ます。エンジンがメモリマップで読む `Assets.zip` は、この読み取り量に入りません。その分はパックの展開時間とハードページフォールトで見ます。 |
| 50 ms・100 ms を超えたフレーム数と最長フレーム | 引っかかりが GC（最悪の 10 秒）と時期が重なるか、JIT やファイル読み取りと重なるかを見て、どちらに手を入れるかを決めます。 |
| 起動からロード完了までの CPU、メインスレッド、JIT、GC、読み取り量、スレッド別の CPU 秒、ハードページフォールト | ロードが 1 本のスレッドで詰まっているか、ディスク、GC、JIT のどれが長いかが分かります。 |
| エンジンの RAM 内訳（マネージドヒープ、ネイティブ、パックのマップ） | RAM を増やして得をする場所があるかを判断します。 |

この計測では決まらないもの：無圧縮テクスチャキャッシュ（MOD のテクスチャキャッシュ ZIP の展開時間はエンジンが数えていません）、異方性フィルタとグラフィックの事前構築（画質の比較が必要です）。これらを測るときは [Windows 実機測定ガイド](windows-waylith-benchmark-ja.md) を使います。

取らないもの：GPU の使用率（エンジンに読み取り口がありません。上のスレッド別の CPU とフレーム上限から、GPU 待ちかどうかは分かります）と、ティック・マップ更新・UI より細かい関数ごとの時間（エンジンのプロファイラーを有効にすると、それ自体がゲームを遅くして値が変わります。この 3 つは呼び出しごとに時計を 2 回読むだけです）。

## 確認した前提（1.7.5011 rev24 の本体 DLL で静的に確認）

1.7.5014 rev1195 は、本体 DLL が R2 にないため参照パッケージ（Krafs.Rimworld.Ref 1.7.5014-unstable）で比べました。この MOD が呼ぶ・パッチする・リフレクションで読むエンジンとゲームの型は、private のものも含めて 5011 と同じ宣言です。ゲーム側で宣言が変わったのはモニター選択、`ModMetaData.GetItemForVersion`、`ShaderDef` だけで、エンジン側はウィンドウ層（GLFW から `Waylith.Windowing` へ）、入力、フレームの提示まわりです。メソッドの中身は参照パッケージにないので比べていません。

- ログは `RimWorld by Ludeon Studios\Logs\Player.log` に書かれ、起動時に前回分が `Player-prev.log` へ移ります（`Waylith.Logging.FileLog`）。1 秒ごとに書き出され、ゲームの実行中でも開けます。
- `GUIUtility.systemCopyBuffer` は GLFW のクリップボードにつながっています（`UnityStubs`）。1.7.5014 では GLFW が外れて Waylith 自身のウィンドウ層に替わりましたが、コピーは実機で働きました（2026-11-20）。
- ゲーム本体の実行ファイルは `RimWorld.exe` です。フォルダに `steam_appid.txt` があるので、Steam が起動していれば直接起動でも Steam に接続できます（Steamworks の通常の仕組み。Workshop の MOD が読み込まれるかは、2 回目の貼り付けの MOD 数で確かめます）。
- オプション画面はゲームを止めます（`Dialog_Options.forcePause`）。プレイ中の平均は、ポーズしていない 10 秒の区間だけを足すので、メニューを開いている間の値は混ざりません。
- 速度 3 の倍率は、入植者が全員寝ていて危険がないとき 12、それ以外は 6 です（`TickManager.TickRateMultiplier`）。目標 TPS が違うので、平均は倍率ごとに分けます。
- ウィンドウが裏にあり「バックグラウンドで実行」が切れているとき、エンジンは更新ごと飛ばします（`EngineApplication.RunFrame`。1.7.5014 ではループが書き直され、フォーカスが外れたときの待ち間隔 `FocusLossIdleInterval` が加わりました。下の 1 秒の規則はどちらにも当てはまります）。戻った最初のフレームの間隔は短く見えるので、フレームの間隔より 1 秒以上長い空きが壁時計で見えたら、その区間を捨てます。「バックグラウンドで実行」が入っているときは更新が続くので、フォーカスが外れた区間を捨てます。
- フレームの間隔（`Time.unscaledDeltaTime`）は、フレーム上限があるとき予定の表示時刻の差です。長いフレームのあとは次の予定が「今 + 1 フレーム」になるので、引っかかりはそのまま数えられます。
- フレーム上限の待ちは、最後の 1〜2 ms ほどを空回りで待ちます（`FrameSleep.SleepUntil`）。そのためフレームが早く終わるとき、メインスレッドの使用率にこの分が少し入ります。描画スレッドを待つ時間（`RenderThread.WaitForBacklogAtMost`）は CPU を使わないので入りません。
- スレッド名は、ゲーム同梱のランタイム（`coreclr.dll`）が Windows のスレッド名（`SetThreadDescription`）に書きます。エンジンは `RenderThread`、`WaylithJob 0`〜（論理 CPU 数 − 1 本）、`AssetPrefetch`、`TextureCacheWriter` と名付けます。スレッドの CPU 時間とハードページフォールトは `NtQuerySystemInformation` の 1 回の呼び出しで読みます（.NET の `Process` クラスが読むものと同じ構造です）。この呼び出しはマシンの全プロセスを列挙するので数 ms かかり、メインスレッドで読んでいた 1 回目と 2 回目は 1 区間あたり 6.8〜7.9 ms でした（.NET の `Process.PrivateMemorySize64` も同じ列挙をするので、その分を含みます）。今は別スレッドで読み、メモリ量は `GetProcessMemoryInfo` で読みます。10 秒の途中で終わったスレッドの分は数えられません。
- GC の種類は起動時に 1 回だけ決まります。環境変数 `DOTNET_gcServer` が、`RimWorld.runtimeconfig.json` の `configProperties` の `System.GC.Server` より優先されます（.NET の通常の規則です。同梱の `coreclr.dll` にも `System.GC.Server` の名前があり、同梱の `hostfxr.dll` と `hostpolicy.dll` がこのファイルを読みます。ゲームが要る `WaylithClr.*` の設定も同じ場所にあります）。
- ゲームのファイルは GC の種類を指定していません（1.7.5011 rev24）。環境変数の指定にランタイムが従うことは、2026-11-20 の 2 回目で確かめました。ファイルの指定は標準の .NET 10 で確かめ（書くと Server、消すと Workstation、`DOTNET_gcServer=0` があればそちらが勝つ）、ゲームでは次の起動で状態欄の「GC の種類」の行で確かめます。
- この MOD は、ファイルに `System.GC.Server` と目印の `MoreUseResources.AddedServerGc` の 2 行だけを足し、ほかは元のとおりに書き戻します。実際の 5011 のファイルで、足してから消すと元のバイト列に戻ることを確かめました。使う JSON の機能（`JsonNode`、`JsonSerializerOptions.NewLine` など）が同梱の `System.Text.Json.dll` にあることも確かめました。
- エンジンの値は公開されているものだけを読みます。RAM の内訳は `Waylith.Diagnostics.ProcessMemoryReport.BuildReport()`、VRAM の内訳は `Waylith.Graphics.GpuMemoryReport.BuildCompactSummary()` で、どちらもエンジン自身がクラッシュレポートやメモリ不足のメッセージに使うものです。パックの統計（`GpuTextureService.PackTextureHits`、`AssetPack.DecodeTicks` など）は、エンジンが詳細ログにだけ書く値と同じです。
- CPU の値は Windows の `GetThreadTimes`（メインスレッド）、`GetSystemTimes`（PC 全体）、`GetProcessIoCounters`（ファイルなどの読み取り量。OS キャッシュから返った分も含み、メモリマップのページ読み込みは入りません）、JIT は .NET の `JitInfo` です。どれも読むだけで、ゲームの動作は変わりません。
- 本 MOD の読み取り量は、先読み、アセット検査（ハッシュ、XML とテクスチャの確認）、パック常駐、XML キャッシュ、小さな状態ファイルの全部を足したものです。ストリームで読むものは、受け取った量を元に、ストリームが OS に頼んだ量を見積もります。
