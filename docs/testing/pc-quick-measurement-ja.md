# PC での短い計測（数値を貼るだけ）

残っている判断（GC の設定、XML キャッシュ、VRAM の使い方）と、実機で未確認の 3 点（状態欄のパック個数、ロード工程の記録、GC の値）を、ゲームを 1 回起動して取ります。所要時間はゲームの起動を含めて約 15 分です。対象は Windows の RimWorld 1.7.5011 rev24 です。

測った値は MOD 設定画面の「状態をコピー」ボタンで、まとめてクリップボードに入ります。手で書き写すものはありません。設定は今のままで構いません（コピーに全設定が入ります）。

後から別の判断が必要になっても測り直さずに済むよう、コピーには、ゲームとエンジンが追加の処理なしで読める値をまとめて入れています。CPU をどこで使っているか（ゲーム全体、メインスレッド、PC 全体、スレッドの種類別）、メインスレッドの時間のうちティック・マップ更新・UI の割合、JIT、ファイルの読み取り、ストレージ待ちのページフォールト、フレームの引っかかり、フレーム上限、起動からロード完了までの内訳、エンジン自身の RAM と VRAM の内訳です。計測そのものにかかった時間も入るので、計測がゲームを遅くしていないかも確かめられます。

## 1. MOD を入れる（初回だけ）

1. GitHub で次の ZIP をダウンロードします。
   `https://github.com/pengin0503/Rimworld-MoreUseResources/archive/refs/heads/main.zip`
2. 展開してできたフォルダの名前を `Rimworld-MoreUseResources` に変えます。
3. Steam のライブラリで RimWorld を右クリックし、「管理」→「ローカルファイルを閲覧」で開いた中の `Mods` フォルダに置きます。古い `Rimworld-MoreUseResources` があれば先に削除します（同じ MOD が 2 つあると読み込みが崩れます）。フォルダ名を同じにすると、MOD の設定は引き継がれます。

## 2. 1 回目（必須）

1. Steam からいつも通り起動し、タイトル画面まで待ちます。
2. いつものセーブをロードします。
3. ゲーム速度を 3（`>>>`）にして、合計 5 分以上プレイします。ポーズ中、メニューを開いている間、別のウィンドウに切り替えている間は数えないので、途中で止めたり Alt+Tab したりしても構いません。
4. Esc →「オプション」→ 左の「MODオプション」→「More Use Resources」（上の検索欄に `More` と入れると早く見つかります）を開き、一番上の **状態をコピー** を押します。
5. 画面左上に「クリップボードにコピーし…」と出たら、このスレッドに Ctrl+V で貼ります。
6. できれば `Player.log` も添付してください（場所は下の「うまくいかないとき」）。他の MOD のログとエラーも入っているので、後から必要になったときに測り直さずに済みます。

## 3. 2 回目（条件付き：Server GC）

貼った中に `この起動中のプレイ … speed 3 x6: … stopped ○○ ms (△△%) … worst 10 s window □□ ms` の行があります（入植者が全員寝ている間は `speed 3 x12` の行に分かれます）。**どちらかの行で △△ が 1 以上、または □□ が 100 以上**のときだけ行います。どちらも下回るときは、GC を変えても得られる量が小さいので不要です。

1. ゲームを終了します。
2. 上の手順で開いたゲームのフォルダで、`RimWorld.exe` を Shift を押しながら右クリックし、「パスとしてコピー」を選びます。
3. スタートボタンを右クリック →「ターミナル」を開き、`$env:DOTNET_gcServer='1'; Start-Process ` と入力した後ろに Ctrl+V で貼って Enter を押します。
4. 1 回目の 2〜5 を同じように行います。貼る前に、GC の行の「モード」が `Server/…` になっていることを見てください。`Workstation/…` のままでも、そのまま貼ってください（設定が効かなかったことが分かります）。
5. この設定はこの起動だけです。次から Steam で起動すれば元に戻ります。

## うまくいかないとき

- **ボタンがない**：古い DLL が読み込まれています。`Mods` に同じ MOD が 2 つないか確認してください。
- **コピーできない、貼れない**：エクスプローラーのアドレス欄に `%USERPROFILE%\AppData\LocalLow\Ludeon Studios\RimWorld by Ludeon Studios\Logs` と入力して開き、`Player.log` をスレッドに添付してください。ボタンを押した時点の内容が `[More Use Resources] Status snapshot:` として同じ形で記録されています。前回の起動のログは `Player-prev.log` です。ゲームを起動するたびに上書きされるので、次に起動する前に添付してください。

## 貼られた値で決めること

| 見る値 | 決めること |
| --- | --- |
| 先読み対象のエンジン用テクスチャキャッシュ・アセットパックの個数 | 0 なら先読みの不具合として直します。1 以上なら、パックの先読みが実機で働いています。 |
| ロード工程の所要時間（`process start to mod`、XML の各工程、`peak working set`） | XML の工程が長ければ XML キャッシュを試す価値があります。`process start to mod`（テクスチャと音声の読み込み）が大半なら、テクスチャ側を優先します。 |
| プレイ中の平均の GC（停止の割合、最悪の 10 秒）と TPS | 2 回目と比べて、Server GC を既定で勧めるかを決めます。 |
| TPS と目標に対する割合（`TPS 300.0 (83% of 360)`。目標は 60 × 速度の倍率） | 100% 近くならゲームは指定の速度で回っていて、CPU を足しても速くなりません。下回っていれば、下の行でどこが詰まっているかを見ます。 |
| VRAM の使用量とドライバー予算、RAM へ退避されたテクスチャ数、エンジンの VRAM 内訳 | 予算に余裕があり退避が 0 なら、VRAM 常駐強化と GPU 先読みの上限を上げる候補にします。退避が出ていれば上げません。 |
| プレイ中のメインスレッドの使用率、ゲーム全体と PC 全体の CPU 使用率 | メインスレッドが 100% 近くで TPS が頭打ちなら、メインスレッドの仕事を減らす方向だけが効きます。PC 全体に空きがあれば、ほかのスレッドへ回せる仕事を探す価値があります。 |
| メインスレッドの時間の内訳（`main thread in ticks …, map update …, UI …`） | ティックが大半ならゲームの計算そのものが重く、この MOD のリソースでは速くなりません。マップ更新（地図の描画と、部屋・電力・光などの更新）が大きければ、描画側の仕事（区画の作り直しの前倒しなど）を調べる価値があります。UI が大きければ、UI を描く MOD を疑います。 |
| スレッド別の CPU（`CPU cores by thread: main …, RenderThread …, WaylithJob (15) …`。値は使っているコア数） | `RenderThread` が 1.00 近くなら描画スレッドが詰まっています。`main` も `RenderThread` も低いのに FPS がフレーム上限より低ければ、GPU 待ちの可能性が高いです（ハードページフォールトが多ければストレージ待ちです）。`WaylithJob` の合計がスレッド数より十分小さければ、エンジンのジョブには空きがあります。`MUR-` で始まるものはこの MOD の分です。 |
| ハードページフォールト（`hard page faults …/s`、起動中の合計） | ゲームがストレージからの読み込みを待った回数です。プレイ中にほぼ 0 なら、`Assets.zip` の RAM 常駐も先読みの強化も効きません。多いときは、空き RAM が少なければメモリ不足（ページファイル）、空きがあれば `Assets.zip` などメモリマップの読み込みなので、常駐を試す価値があります。 |
| フレーム上限（コピーの先頭の `frame cap`） | FPS が上限と同じなら、メインスレッドは待っている時間があり、FPS は上がりません。 |
| 計測にかかった時間（`measuring took … ms per window`） | 1 区間（10 秒）あたりの値です。数 ms を超えていたら、計測を軽くします。 |
| プレイ中と起動中の JIT の時間 | 合計が大きければ JIT の先行コンパイルを試す価値があります。小さければ不要です。 |
| プレイ中の読み取り量（`I/O read`、括弧内の本 MOD 分を差し引いて見る）とパックの展開時間 | プレイ中もゲームがファイルを読んでいれば、OS キャッシュへの先読みを続ける意味があります。この量は OS キャッシュから返った分も含むので、ストレージまで行ったかはハードページフォールトと合わせて見ます。エンジンがメモリマップで読む `Assets.zip` は、この読み取り量に入りません。その分はパックの展開時間とハードページフォールトで見ます。 |
| 50 ms・100 ms を超えたフレーム数と最長フレーム | 引っかかりが GC（最悪の 10 秒）と時期が重なるか、JIT やファイル読み取りと重なるかを見て、どちらに手を入れるかを決めます。 |
| 起動からロード完了までの CPU、メインスレッド、JIT、GC、読み取り量、スレッド別の CPU 秒、ハードページフォールト | ロードが 1 本のスレッドで詰まっているか、ディスク、GC、JIT のどれが長いかが分かります。 |
| エンジンの RAM 内訳（マネージドヒープ、ネイティブ、パックのマップ） | RAM を増やして得をする場所があるかを判断します。 |

この計測では決まらないもの：無圧縮テクスチャキャッシュ（MOD のテクスチャキャッシュ ZIP の展開時間はエンジンが数えていません）、異方性フィルタとグラフィックの事前構築（画質の比較が必要です）。これらを測るときは [Windows 実機測定ガイド](windows-waylith-benchmark-ja.md) を使います。

取らないもの：GPU の使用率（エンジンに読み取り口がありません。上のスレッド別の CPU とフレーム上限から、GPU 待ちかどうかは分かります）と、ティック・マップ更新・UI より細かい関数ごとの時間（エンジンのプロファイラーを有効にすると、それ自体がゲームを遅くして値が変わります。この 3 つは呼び出しごとに時計を 2 回読むだけです）。

## 確認した前提（1.7.5011 rev24 の本体 DLL で静的に確認）

- ログは `RimWorld by Ludeon Studios\Logs\Player.log` に書かれ、起動時に前回分が `Player-prev.log` へ移ります（`Waylith.Logging.FileLog`）。1 秒ごとに書き出され、ゲームの実行中でも開けます。
- `GUIUtility.systemCopyBuffer` は GLFW のクリップボードにつながっています（`UnityStubs`）。
- ゲーム本体の実行ファイルは `RimWorld.exe` です。フォルダに `steam_appid.txt` があるので、Steam が起動していれば直接起動でも Steam に接続できます（Steamworks の通常の仕組み。Workshop の MOD が読み込まれるかは、2 回目の貼り付けの MOD 数で確かめます）。
- オプション画面はゲームを止めます（`Dialog_Options.forcePause`）。プレイ中の平均は、ポーズしていない 10 秒の区間だけを足すので、メニューを開いている間の値は混ざりません。
- 速度 3 の倍率は、入植者が全員寝ていて危険がないとき 12、それ以外は 6 です（`TickManager.TickRateMultiplier`）。目標 TPS が違うので、平均は倍率ごとに分けます。
- ウィンドウが裏にあり「バックグラウンドで実行」が切れているとき、エンジンは更新ごと飛ばします（`EngineApplication.RunFrame`）。戻った最初のフレームの間隔は短く見えるので、フレームの間隔より 1 秒以上長い空きが壁時計で見えたら、その区間を捨てます。「バックグラウンドで実行」が入っているときは更新が続くので、フォーカスが外れた区間を捨てます。
- フレームの間隔（`Time.unscaledDeltaTime`）は、フレーム上限があるとき予定の表示時刻の差です。長いフレームのあとは次の予定が「今 + 1 フレーム」になるので、引っかかりはそのまま数えられます。
- フレーム上限の待ちは、最後の 1〜2 ms ほどを空回りで待ちます（`FrameSleep.SleepUntil`）。そのためフレームが早く終わるとき、メインスレッドの使用率にこの分が少し入ります。描画スレッドを待つ時間（`RenderThread.WaitForBacklogAtMost`）は CPU を使わないので入りません。
- スレッド名は、ゲーム同梱のランタイム（`coreclr.dll`）が Windows のスレッド名（`SetThreadDescription`）に書きます。エンジンは `RenderThread`、`WaylithJob 0`〜（論理 CPU 数 − 1 本）、`AssetPrefetch`、`TextureCacheWriter` と名付けます。スレッドの CPU 時間とハードページフォールトは `NtQuerySystemInformation` の 1 回の呼び出しで読みます（.NET の `Process` クラスが読むものと同じ構造です）。10 秒の途中で終わったスレッドの分は数えられません。
- `RimWorld.runtimeconfig.json` は GC の種類を指定していないので、`DOTNET_gcServer` を妨げる設定はありません。ただしランタイムが実際に従うかは未確認なので、2 回目で GC の行を確認します。
- エンジンの値は公開されているものだけを読みます。RAM の内訳は `Waylith.Diagnostics.ProcessMemoryReport.BuildReport()`、VRAM の内訳は `Waylith.Graphics.GpuMemoryReport.BuildCompactSummary()` で、どちらもエンジン自身がクラッシュレポートやメモリ不足のメッセージに使うものです。パックの統計（`GpuTextureService.PackTextureHits`、`AssetPack.DecodeTicks` など）は、エンジンが詳細ログにだけ書く値と同じです。
- CPU の値は Windows の `GetThreadTimes`（メインスレッド）、`GetSystemTimes`（PC 全体）、`GetProcessIoCounters`（ファイルなどの読み取り量。OS キャッシュから返った分も含み、メモリマップのページ読み込みは入りません）、JIT は .NET の `JitInfo` です。どれも読むだけで、ゲームの動作は変わりません。
- 本 MOD の読み取り量は、先読み、アセット検査（ハッシュ、XML とテクスチャの確認）、パック常駐、XML キャッシュ、小さな状態ファイルの全部を足したものです。ストリームで読むものは、受け取った量を元に、ストリームが OS に頼んだ量を見積もります。
