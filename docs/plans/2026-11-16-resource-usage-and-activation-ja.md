# Rimworld-MoreUseResources — リソース積極活用MOD 開発計画

- 作成日: 2026-11-16
- 状態: **計画／設計**（MOD本体は未実装・未検証）
- 対象: RimWorld Windows **1.7.5011 rev24**
- 参照ゲーム本体: Cloudflare R2 `rimworld-17/Game-Windows/`（読み取りのみ）
- 対象PCの例: Ryzen 7 9700X（8コア16スレッド）、Radeon RX 7800 XT（VRAM 16GB）、RAM 32GB
- 実装するMODのリポジトリ: `pengin0503/Rimworld-MoreUseResources`

## 1. 目的と仕様の優先順位

**TPS、FPS、ロード時間の高速化は必須要件にしない。** ユーザーの目的は、RimWorldがロード中にRAM約3GiBしか使っていないように見える状況を含め、PCの空いているCPU・RAM・GPU/VRAMをより積極的に活用すること。

利用タイミングは**起動・ロード時に限定しない**。タイトル画面、通常プレイ、加速中、ポーズ中、ワールド画面、マップ切替、セーブ中、操作がない時間などを**個別に有効・無効設定**できるようにする。

性能改善を採用条件としない一方、ゲーム結果やセーブの破損、操作不能、過度なスワップ、OSの極端な応答低下、過熱は許容しない。CPU・GPU・RAMの使用率増加だけを高速化の証拠として扱わない。

### 利用方式を明確に区別する

1. **実作業／キャッシュモード（基本）**: ゲームが使用する可能性のあるデータの先読み、独立した読み取り専用解析・索引作成、上限付きキャッシュ、検証可能な描画リソースのウォームアップを行う。処理がなくなればリソース使用量も下がり得る。
2. **使用量優先モード（オプション）**: 実際の有用データが少なくても、ユーザー設定の範囲でRAMを予約することを許す。**予約だけではゲームを高速化しない**とUIに明記。実装する場合、段階的確保・圧迫時解放・終了時解放を必須とし、初期値はOFF。
3. **負荷試験モード（実験用・任意）**: CPU/GPUの純粋な負荷生成はゲーム改善用の処理とは別機能として明示し、ゲームプレイ中の標準動作に混ぜない。VRAMの単なる占有も性能向上を意味しない。GPU処理APIの検証ができない場合は未実装扱いにする。

## 2. 新版Windowsの確認済み前提

R2の実ファイルから確認済み: `Game-Windows/Version.txt` は `1.7.5011 rev24`、`RimWorld.runtimeconfig.json` は `net10.0` と `10.0.15-waylithclr.dev` を参照、`Assembly-CSharp.dll` は15,637,504 bytes。Waylith/UnityStubs関係DLLも存在する。

新版のDLL内には `TickManagerUpdate`、`DoSingleTick`、`JobTrackerTick`、`TrySetNewPathRequest`、`MapMeshDirty` などの文字列がある。ただし、存在確認はパッチ可否・完全署名・実行スレッド・安全性の証明ではない。

旧版監査資料は `research/vanilla-1.7.4985-audited/START-HERE.md`、`systems/tick-performance.md`、`systems/jobs-pathfinding.md`、`systems/ui-harmony-waylith.md` にある。**旧版1.7.4985の分析結果は新版にそのまま適用せず、差分を照合**する。既存テストホスト `pengin0503/RimWorld-for-mod-test` はLinux旧版向けの適格化が中心であり、新版Windowsを起動して完全検証できるものではない。

## 3. 「いつ使用するか」の設定仕様

### 3.1 画面に設ける設定

- 全体: `リソース積極活用を有効化`（マスタースイッチ）。
- リソース種別: `RAM` / `CPU` / `GPU` を個別ON/OFF（GPUは対応機能が確認できた場合のみ有効化可能）。
- 動作段階: 下表の各チェックボックス。複数同時選択可。
- 動作強度: `控えめ` / `標準` / `積極的` / `カスタム`。
- CPU設定: ワーカー数上限、ゲームメインスレッドを妨げない待機・休止ルール、タスクの1回あたり時間予算。
- RAM設定: 上限GiB、目標使用量（上限との違いを説明）、ゲーム/OSメモリ余裕の下限、キャッシュ方式、任意の予約モード。
- GPU設定: 利用可能な描画リソース先読み、VRAM予算、サポートされている処理のみ選択可能。対応不可なら無効状態と理由を表示。
- 手動操作: `いま実行`、`一時停止`、`保持キャッシュを解放`、`自動制御に戻す`。
- 状態表示: 現在フェーズ、適用中のルール、使用中キャッシュ容量、ワーカー数、タスク進捗、失敗・自動停止理由。RAM値は「MODが保持したキャッシュ」と「プロセス全体の使用RAM」を区別する。

### 3.2 適用タイミング（すべて個別チェック）

| 設定項目 | 想定する動作 | 初期設定案 |
|---|---|---|
| ゲーム起動後の初期化 | MODがロードされ、設定読込可能になってから事前準備 | ON |
| タイトル画面 | バックグラウンドで先読み・索引構築 | ON |
| セーブのロード中 | 安全な独立処理と限定キャッシュのみ | ON |
| マップ生成・マップ切替 | 事前準備、切替後の再ウォームアップ | ON |
| **通常プレイ中** | 継続的な有用前処理・キャッシュ保持 | **ON** |
| **高速プレイ中** | 頻度・強度を別設定。ゲーム本体を阻害しない | **ON** |
| **ポーズ中** | キャッシュの拡充、先読みなどを積極的に実施 | **ON** |
| ワールド画面表示中 | ワールド向けの独立作業のみ | ON |
| キャラバン・遠征先操作中 | マップ・ワールドごとの安全なキャッシュ | ON |
| 操作なしのアイドル時 | 一定時間操作がなければ強度を上げる | OFF |
| セーブ／オートセーブ中 | 書込競合しない保持作業だけを許可 | OFF |
| ゲーム終了処理中 | 新規タスクは禁止、解放のみ実施 | 固定OFF |

上記の初期設定案は**未実装時点の仕様案**。ゲームに導入する際にデフォルトを確定する。ユーザーは後から各項目を自由にON/OFFにでき、変更は原則その場で反映する。

「ゲーム起動後」はMODが初期化済みの時点から。MOD自身がロードされる**前のプロセス起動やMOD読込初期段階に介入するには別途ブートストラップ実装が必要**であり、現段階では保証しない。

### 3.3 フェーズが重なる場合のルール

ゲームの状態を排他的に判定し、以下の優先順位で適用する。

1. 終了中・エラー停止・メモリ危険状態 → 新規仕事を中止、必要ならキャッシュ解放
2. セーブ中 → セーブ専用ルール
3. ロード中／マップ生成中 → ロード・生成専用ルール
4. ポーズ中 → ポーズ設定
5. 高速プレイ中 → 高速設定
6. 通常プレイ中 → 通常設定
7. タイトル画面 → タイトル設定

`ワールド画面`、`キャラバン`、`アイドル` は補助条件とし、現在の主フェーズと設定の両方がONの場合のみ作業を有効化する（例: 通常プレイON・ワールド画面OFFならワールド画面では抑制）。例外や遷移時は安全側へ倒す。ゲーム内時間・時刻によるスケジュールは将来拡張に分離する。

## 4. リソースごとの実装方針

### 4.1 RAM

- メインは実データを保持する**上限付き先読みキャッシュ**。MODデータ索引、読み取り専用で世代管理可能なスナップショット、ゲーム本体が合法的に先読みできるリソースなどを候補とする。
- 起動・ロード後だけでなく**通常プレイ中にも保持・再利用**。マップ切替、Def変更、ロード、MOD設定変更で適切に破棄・再構築する。
- 当初のカスタム予算例: 追加キャッシュ上限 **4GiB**（ユーザー設定で変更可）、OS空きRAMの安全マージン **6GiB以上**。32GiB搭載PC向けの実験案であり、計測して調整する。
- 目標容量と上限容量を区別。実データが4GiBに達しなければ、実作業モードでは無理に埋めない。「RAM予約モード」は別の明示操作でのみ選択する。
- FIFOではなくLRU等、キャッシュごとの重み、上限解放、メモリ圧迫時の縮小、スロットリング検知、GCの負荷を計測する。ゲームのオブジェクトを無条件に保持してマップ破棄を妨げない。
- OS側の「使用RAM」、プロセスWorking Set、Private Bytes、GC Heap、MOD専用キャッシュ量は一致しない。表示では混同しない。

### 4.2 CPU

- 起動・ロード・メニュー・プレイ中・ポーズ中の各段階で、**先読み、索引生成、整合性照合、スナップショットの純粋な計算**などをワーカーで実行。
- 実際に処理できるタスクがない時間はCPU使用率を強制的に維持しない。使用率そのものを上げたい場合は、実験的負荷試験モードに分離する。
- 作業は `メインスレッドでデータを安全にコピー → ワーカースレッドで独立計算 → 必要時のみメインスレッドへ反映` の段階に分ける。
- `Verse.Map`、`Pawn`、`DefDatabase`、`Rand`、セーブ処理、描画APIなどをワーカースレッドから無条件に呼ばない。
- Windows実機のCPUコア数と空き状況からワーカー数を調整。上限、処理時間、処理優先度、キューの長さをユーザー設定にする。ポーズ中は強く、プレイ中はゲームの反応に応じて抑制できる。
- ゲームロード／メインメニュー移行／マップ破棄時にキャンセルトークンと世代番号で前フェーズの仕事を無効化。既存のWaylithや他MODが並列処理する経路に二重介入しない。

### 4.3 GPU/VRAM

- `Waylith`/Vulkanの**検証済み**描画経路・リソース管理APIを経由して、妥当なテクスチャや描画資源の先読み・保持・ウォームアップなどを検討。
- GPUはCPUのようにC#のスレッド数だけ増やして使用率を上げられない。ゲームの描画スレッド・GPUコンテキスト所有権を尊重し、GPUリソースの作成・解放場所を固定する。
- シェーダ／コンピュート処理を新設する場合は、対応API、同期、転送、メモリ管理の調査とWindows RX 7800 XT実機検証を必須とする。
- GPU負荷を増やすだけの意味のない描画・計算は基本モードには入れない。試験モードが必要なら「ゲーム高速化の効果なし・描画遅延の恐れあり」を明記し、デフォルトOFF。
- VRAM使用量はOS・ドライバ・Waylithの実装によって測定方法が異なる。正確な計測が提供できない場合、値を捏造せず「取得不可」と表示。
- 対応を実証できるまではGPUチェックボックスを使用不可にし、CPU/RAMだけでMODが成立するようにする。

## 5. 設定と状態管理の実装案

```text
Rimworld-MoreUseResources/
  About/About.xml
  Source/
    Settings/          # ModSettings保存、強度、各フェーズ個別ON/OFF
    Lifecycle/         # GameState観測、フェーズ遷移、ゲーム内状態の安全な判断
    Scheduler/         # 優先度付き仕事キュー、ワーカー数・時間予算、キャンセル
    Resources/Ram/     # 先読み・キャッシュ・予算・解放・任意の明示RAM予約
    Resources/Cpu/     # 純粋な並列処理とアイドル制御
    Resources/Gpu/     # 対応APIを確認できた場合に限る
    Diagnostics/       # モード、リソース使用量、例外、自動停止理由
    Compatibility/     # Waylith、Harmony、WOWGAG等の干渉調査
  Tests/
    Settings/
    LifecycleTransitions/
    ResourceBudgets/
    Cancellation/
    SaveLoadSafety/
  docs/
    research/
    plans/
```

動作フロー:

`DetectPhase → CheckEnabledForPhase → CheckResourceBudget → EnqueueUsefulWork → ObserveMetrics → ThrottleOrRelease → OnPhaseChangedCancelAndReconfigure`

設定はゲーム再起動後も保持。変更時には次の周期／状態遷移で反映し、一時停止・キャッシュ解放は即時反映する。変更不能な初期化段階はUIに明記する。

## 6. 受け入れ条件（速度改善は要求しない）

- 通常プレイ中を含め、選択したフェーズで**選択したリソース**の仕事が開始され、非選択フェーズでは開始されない。
- RAMキャッシュ上限が守られ、設定を下げると保持データを解放できる。OS空きRAMが減少すれば自動縮小する。
- CPUは指定したワーカー数・強度を越えず、終了・ロード・モード変更で安全にキャンセルできる。
- GPUが実装・対応されていなければUIにそのまま表示する。GPU動作成功を偽らない。
- 使用量が増えない場合も原因（対象タスクなし、キャッシュ上限、API非対応、OS制限）を表示する。
- セーブ・ロード・コロニー切替・ゲーム終了の整合性を損なわない。バックグラウンド仕事はセーブ対象にせず、必要なら再構築する。
- WOWGAG・Harmonyなどの併用時にゲーム側の非スレッドセーフ処理へ触れない。事故時は個別機能を停止する。
- TPS/FPSの改善率をリリース条件にしない。問題のある操作遅延・メモリ圧迫・クラッシュは受け入れない。

## 7. 開発フェーズ

| 段階 | 完了物 |
|---|---|
| P0 | Windows 1.7.5011の完全シグネチャ/IL・ライフサイクル確認、利用可能API一覧 |
| P1 | 設定UI、フェーズ検出、開始／停止の状態遷移、診断表示（計算負荷なし） |
| P2 | RAMキャッシュとメモリ予算の実装、プレイ中の保持と解放 |
| P3 | CPUの有用な並列バックグラウンド仕事、キャンセルと負荷制限 |
| P4 | 明示オプションのRAM予約、使用量優先設定（安全弁付き） |
| P5 | WaylithのGPU/VRAM対応APIを検証し、可能な機能のみ追加 |
| P6 | セーブ／ロード／切替・長時間プレイ・MOD併用のWindows実機検証 |

**この計画の時点でゲーム用DLLの完全IL解析・Windows実行試験・GPU動作確認は未実施。実装まで完了したという意味ではない。**

## 8. Colabとの役割分担

- Colab CPU: R2の新Windows版DLLを読み取り、IL/型情報・キャッシュ対象・MOD衝突を解析する。
- Colab GPU: 必要ならローカルLLMでソースコードレビューや比較評価を行う。
- **ColabのGPU/CPU/RAMはユーザーPCのゲーム実行時リソースを増やすものではない**。最終的な動作・使用RAM・VRAM・負荷評価はWindows実機で行う。
- R2本体と旧研究索引は読み取り専用。アクセスキー・個人情報をGitHubやログに保存しない。

## 9. 実装開始時に最初に確認すること

1. R2 `Game-Windows/Version.txt` を確認して版を固定する。
2. 新版 `Assembly-CSharp.dll` と `Waylith.dll` を解析し、MOD設定を読み込めるタイミングとタイトル／ロード／プレイ／ポーズ／ワールド／セーブ遷移の安全な観測方法を確定する。
3. 他MODとの競合箇所と既存ワーカー・キャッシュの有無を調査する。
4. GPU対応可否を切り分け、未確認の機能はUIから選べないようにする。
5. P1のフェーズ別ON/OFFと診断を先に完成させ、その後にRAM/CPU/GPUの個別実装を進める。
