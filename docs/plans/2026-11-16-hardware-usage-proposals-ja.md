# ハードウェア使用量を上げて全体を改善する提案（2026-11-16）

- 状態: **PR #5で実装・単体検証済み**。Windows実機での動作・効果は未計測。
- 基準: RimWorld Windows 1.7.5011 rev24 / .NET 10 / Waylith
- 根拠: 本体 DLL の逆コンパイルによる静的確認。**実機での効果はどれも未計測**。
- 想定環境: Ryzen 16 スレッド、Radeon RX 7800 XT（VRAM 16 GB）、RAM 32 GB、MOD 約 279 個。

## 前提として確認した事実

- RAM を多く使うこと自体ではロードは速くならない。ロード中の使用量が 3 GiB 程度なのは、その時点で必要なデータがそれだけしかないため。1.7 はテクスチャをロード時に展開せず、使うときに読む（OnDemand）。
- ゲームは一度変換したテクスチャを `<キャッシュ保存先>/TextureCache/v<番号>/<圧縮設定>/<MODフォルダ名>-<16桁>.zip`（LZ4）に保存し、次回以降はソース PNG を開かない。プレイ中の読み込みはメインスレッドがこの ZIP から行う。
- 公式コンテンツは `Assets.zip` にあり、エンジンが読み取り専用でメモリマップしている。
- エンジンには並列先読み `AssetPrefetcher`（最大 8 ワーカー、保持 64 MiB 固定）が既にある。
- MOD クラスの生成は `LoadModContent`（テクスチャ・音声）の後、`LoadModXML` の前。初回のテクスチャ読み込みには MOD から介入できない。XML 以降には Harmony で介入できる。
- `RimWorld.runtimeconfig.json` に GC の指定はなく、.NET の既定値（Workstation GC）で動く。
- Harmony を適用できるのは `Assembly-CSharp` のみ（`WaylithClr.JitPatchableAssemblies`）。

## 実装仕様と残る検証

| 提案 | 実装・互換条件 | 実機で確認する項目 |
| --- | --- | --- |
| 1. GC設定 | `Start-RimWorldGc.ps1` が子プロセスにWorkstation／Serverと任意のServerヒープ数を設定。GC設定の恒久変更は不要。状態欄で実際のGC種類と、同じフェーズの保存基準との差を表示。GC世代の内部予算は公開された起動設定だけで調整する方針とした。 | WaylithCLRでServerとヒープ数設定が効くこと、同じセーブ・ゲーム速度のGC停止回数／時間とRAM使用量。 |
| 2. 無圧縮テクスチャキャッシュ | `TextureCacheStore.Store` が各書き込み時に `CacheCodec` を読み、各ZIPエントリに方式を記録する。MOD初期化後の書き込みを `None` に切替。初期の `LoadModContent` はMOD初期化より前に走る。既存エントリと初期化前に完了した書き込みには従来の方式が残る。OFFと終了でMODが変更した設定を復元。 | 圧縮・無圧縮混在ZIPの読み込み、既存エントリ再利用、ディスク容量、実際のアップロード時間。 |
| 3. JIT先行コンパイル | 通常の管理メソッドを対象に `PrepareMethod`。開いたジェネリック、コンストラクタ、抽象、P/Invoke、既知のHarmony対象を除外。最大2共有ワーカー、合計8,000件・アセンブリごと1,024件。フェーズ、フレームガード、空きRAMを処理直前に再確認。 | カスタムランタイムでの成功率、初回のヒッチとコード領域の増加。進行中の単一JIT呼び出しは完了まで実行される。 |
| 4. XMLキャッシュ | 初期OFF。XML読込・結合・TKey解析・エラー確認・Def生成は既存工程を使う。成功した標準パッチの適用結果とルートノードの由来を、ノード型とテキスト境界を保つ形式で保存。独自パッチ、外部の関連Harmonyパッチ、TKeyの参照状態、無効化入力、破損、ホットリロードは通常ロード。キャッシュは1ファイル・最大64MiB。 | 同一構成2回目のヒット、MOD順序／Defs／Patches／設定変更での失効、適用時間と総ロード時間。 |
| 5. VRAM常駐 | 公開ポリシーは `OffloadUnderPressure` と `OnDemand`。前者のときに先読みの上限を75%まで許可し、後者や予算不足では追加の引き上げを解除。エンジンの退避は稼働し続ける。 | 実VRAM増加、予算縮小や他アプリ使用時の後退、退避後の再読み込みヒッチ。 |
| 6. グラフィック事前構築 | 初期OFF。Waylithの通常ロードで用意済みの基本グラフィックに加え、添付と一部の建物用の `Graphic_Single`・`Graphic_Multi` を対象にする。タイトル／ポーズ中に共有フレーム予算内で処理し、実構築の後にVRAMを再計測。関連グラフィック生成にHarmonyパッチがあればスキップ。 | タイトル／ポーズ中の所要時間と、対応する設備を初めて表示したときのフレーム時間。 |
| 7. 画質 | Unity互換のグローバルミップ上限はスタブ。WaylithのVulkanメッシュ描画が参照するテクスチャ単位の `anisoLevel` を最大4×にする。既存ディスクリプタの再生成にはrev24のテクスチャ世代を使い、解除も同じ経路で反映。公開設定と描画の実装を優先し、既存の画質MODは検出時に優先する。 | 対象テクスチャの斜め方向の見え方、Vulkanサンプラーと負荷、OFF時の復元。 |

## 採用しないもの

- **展開済みテクスチャをゲームのテクスチャへ直接渡す**: キャッシュ読み出しがエンジン内部 API。公開 API でデータを持たせると `isReadable` が変わり、本体のアトラス生成などの分岐が変わる。
- **テクスチャキャッシュ ZIP のメモリマップ**: エンジンが `SetLength` と置換で書き換えるため、Windows で失敗させる恐れがある。
- **Pawn の処理の並列化**: Overclock などと競合し、ゲーム結果が変わり得る。
- **セーブの並列化**: セーブ保護に触れる。

## 実機の検証順序

1. 全設定OFFで起動し、ロード計測とGCの基準を取得する。
2. GC、JIT、無圧縮、XML、VRAM、グラフィック準備、画質を個別にONにして、上表の項目を確認する。
3. セーブ、ポーズ解除、ホットリロード、機能OFF、空きRAMとVRAMの低下、ゲーム終了を確認する。
