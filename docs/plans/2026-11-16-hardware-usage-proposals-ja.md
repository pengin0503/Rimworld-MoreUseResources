# ハードウェア使用量を上げて全体を改善する提案（2026-11-16）

- 状態: **提案**。下記「実装済み」を除き未実装。
- 基準: RimWorld Windows 1.7.5011 rev24 / .NET 10 / Waylith
- 根拠: 本体 DLL の逆コンパイルによる静的確認。**実機での効果はどれも未計測**。
- 想定環境: Ryzen 16 スレッド、Radeon RX 7800 XT（VRAM 16 GB）、RAM 32 GB、MOD 約 279 個。

## 前提として確認した事実

- RAM を多く使うこと自体ではロードは速くならない。ロード中の使用量が 3 GiB 程度なのは、その時点で必要なデータがそれだけしかないため。1.7 はテクスチャをロード時に展開せず、使うときに読む（OnDemand）。
- ゲームは一度変換したテクスチャを `<キャッシュ保存先>/TextureCache/v<番号>/<圧縮設定>/<MODフォルダ名>-<16桁>.zip`（LZ4）に保存し、次回以降はソース PNG を開かない。プレイ中の読み込みはメインスレッドがこの ZIP から行う。
- 公式コンテンツは `Assets.zip` にあり、エンジンが読み取り専用でメモリマップしている。
- エンジンには並列先読み `AssetPrefetcher`（最大 8 ワーカー、保持 64 MiB 固定）が既にある。
- MOD クラスの生成は `LoadModContent`（テクスチャ・音声）の後、`LoadModXML` の前。初回のテクスチャ読み込みには MOD から介入できない。XML 以降には Harmony で介入できる。
- `RimWorld.runtimeconfig.json` に GC の指定はなく、.NET の既定値（Workstation GC）で動く。
- Harmony を適用できるのは `Assembly-CSharp` のみ（`WaylithClr.JitPatchableAssemblies`）。

## 実装済み（PR #5）

## 提案

### 1. GC の設定を RAM 寄りにする（RAM → カクつき・TPS）

- **内容**: 第 0 世代の予算を広げる、Server GC にするなどで、RAM を数 GiB 多く使う代わりに GC の回数と停止を減らす。
- **手段**: 起動時の環境変数（`DOTNET_GCgen0size`、`DOTNET_gcServer`、`DOTNET_GCgen0MaxBudget` など）。実行中に MOD から変えられるのは遅延モード（実装済みの `RamGcLowLatency`）に限られる。
- **MOD の役割**: 計測表示（実装済み）、設定方法の案内、設定前後の比較表示。
- **未確認**: Waylith の独自ランタイム（`10.0.15-waylithclr.dev`）が `DOTNET_` 環境変数を受け付けるか。Server GC は論理コア数ぶんのヒープを持つため、メモリ使用量とメインスレッドへの影響を実測する必要がある。
- **リスク**: 小。設定はゲーム外で、外せば元に戻る。
- **次の一歩**: 実機で GC 計測の値を取り、停止時間の割合が大きければ環境変数を試す。

### 2. テクスチャキャッシュを無圧縮にする（ディスク・RAM → 読み込み時の CPU）

- **内容**: `GpuTextureService.CacheCodec`（公開、既定 `Lz4`）を `None` にする。読み込み時の LZ4 展開がなくなる。
- **代償**: キャッシュ ZIP が大きくなり、ディスクと OS キャッシュの使用量が増える。既存キャッシュが新しい形式で書き直されるかは未確認。
- **リスク**: 中。キャッシュ形式の切り替え時の挙動を実機で確認する必要がある。LZ4 の展開は速いので効果は小さい可能性がある。
- **次の一歩**: `TextureCacheStore` のエントリ単位のコーデック扱いを読み、混在が安全か確かめる。

### 3. JIT の先行コンパイル（CPU の空きコア・RAM → 初回実行時のひっかかり）

- **内容**: タイトル画面やポーズ中に、本体と MOD のメソッドを低優先度ワーカーで `RuntimeHelpers.PrepareMethod` する。
- **代償**: CPU を実際に使う。コード領域として RAM が数百 MiB 増える。
- **注意点**: ジェネリックの未確定メソッド、抽象メソッド、P/Invoke は対象外にする。Harmony が後から書き換えるメソッドは再コンパイルされるので害はないが、無駄になる。静的コンストラクタを早く走らせないこと（`PrepareMethod` は走らせない）。階層型コンパイルの最適化段までは進められない。
- **リスク**: 小〜中。ゲーム状態には触れない。既存のフェーズ制御とフレームガードに載せる。
- **次の一歩**: 対象アセンブリとメソッドの絞り込み規則を決め、件数と所要時間を状態欄に出す。

### 4. パッチ適用後 XML のキャッシュ（ディスク・CPU → ロード時間）

- **内容**: MOD 構成と全 XML のハッシュが前回と同じなら、`LoadModXML`・`CombineIntoUnifiedXML`・`ApplyPatches` の結果を保存しておいて読み込む。既存の SHA-256 索引を鍵に使える。
- **期待**: MOD 数が多い環境ではロード時間への効果が最も大きい見込み。ただし内訳は未計測で、ロード工程の計測結果を見てから着手する。
- **リスク**: 大。Harmony で本体のロード処理を差し替える。MOD 設定や他 MOD の有無で結果が変わるパッチ、ロード処理に手を入れる他 MOD、エラー表示用の `assetlookup` の再現が課題。鍵には MOD 一覧、読み込み順、各ファイルのハッシュ、本体バージョン、MOD 設定ファイルを含める必要がある。
- **条件**: 実験機能、初期 OFF。実機検証が済むまでマージしない。不一致や例外があれば通常のロードに戻す。

### 5. テクスチャを VRAM から退避させない（VRAM → プレイ中の再読み込み）

- **内容**: `TextureResidency.Policy`（公開、既定 `OffloadUnderPressure`）を退避しない側に寄せる。あわせて既存の GPU 先読みで VRAM を埋める。
- **代償**: VRAM 使用量が増える。VRAM が足りなくなった場合の挙動はエンジン任せになる。
- **リスク**: 中。既存の VRAM 予算監視と組み合わせ、残り容量が下限を切ったら既定の方針に戻す。
- **次の一歩**: `TextureResidencyPolicy` の各値と、予算超過時の動作を読む。

### 6. グラフィック資源の事前構築（RAM・VRAM → 初めて画面に出たときのひっかかり）

- **内容**: 全 `ThingDef` のグラフィックとマテリアル、ポートレートなどを、フレーム時間の予算内でメインスレッドから少しずつ先に作る。
- **代償**: RAM と VRAM が増える。メインスレッドの時間を使う。
- **リスク**: 中〜大。他 MOD の描画コードを通常と違うタイミングで呼ぶことになる。例外は握りつぶさず、その Def を飛ばして記録する。
- **条件**: 実験機能、初期 OFF。タイトル画面とポーズ中に限定して始める。

### 7. 余った GPU を画質に回す（GPU → 見た目）

- **内容**: 異方性フィルタ、ミップの品質など。速度ではなく見た目の改善。
- **未調査**: エンジンが公開している画質設定。Graphics Settings+ など既存 MOD との重複。
- **次の一歩**: 公開設定の一覧を作り、既存 MOD が扱っていない項目だけを対象にする。

## 推奨する順番

1. 実機で PR #5 を起動し、ロード工程の計測と GC 計測の値を取る。
2. 提案 1（環境変数の試行）と提案 3（JIT 先行コンパイル）。
3. 計測でパッチ適用が支配的なら提案 4 を設計する。
4. 提案 5、2、6、7 は VRAM と RAM の実測値を見てから。

## 採用しないもの

- **展開済みテクスチャをゲームのテクスチャへ直接渡す**: キャッシュ読み出しがエンジン内部 API。公開 API でデータを持たせると `isReadable` が変わり、本体のアトラス生成などの分岐が変わる。
- **テクスチャキャッシュ ZIP のメモリマップ**: エンジンが `SetLength` と置換で書き換えるため、Windows で失敗させる恐れがある。
- **Pawn の処理の並列化**: Overclock などと競合し、ゲーム結果が変わり得る。
- **セーブの並列化**: セーブ保護に触れる。
