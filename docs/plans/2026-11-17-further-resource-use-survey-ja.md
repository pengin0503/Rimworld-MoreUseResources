# さらに資源を使える既存処理の調査（2026-11-17）

対象: RimWorld Windows 1.7.5011 rev24 / Waylith。本体・エンジンの逆コンパイルと、受領したWOWGAG・Overclock・Axenの配布DLLに基づく静的な調査です。実機での計測はしていません。「使える」と書いた項目も、効果は未計測です。

判断の基準は、これまでと同じです。本体が実際に消費している処理を前倒し・保持・増枠できるものだけを候補にし、新しい集計や合成負荷は候補にしません。

## 結論

エンジン側の調整口はほとんど残っていません。Waylithの並列数・予算・しきい値は定数で、HarmonyはAssembly-CSharpにしか適用できないためです（`WaylithClr.JitPatchableAssemblies=Assembly-CSharp`）。残る候補は次の3件で、上から順に確度が高いと判断します。

| 順位 | 候補 | 使う資源 | 実装の規模 | 主な不確実性 |
| --- | --- | --- | --- | --- |
| 1 | 起動スクリプトでGCの第0世代の予算を広げる | RAM | 小（スクリプトの引数1つ） | WaylithのカスタムCLRがこの設定を読むか |
| 2 | Vulkanパイプラインキャッシュを起動間で引き継ぐ | ディスク、RAM、起動後のCPU | 中（エンジン内部への反射とネイティブ呼び出し） | GPUドライバー自身のキャッシュと効果が重なる可能性 |
| 3 | 既存機能の上限を引き上げる設定 | CPU、VRAM | 小（上限値と設定項目） | フレーム時間への影響 |

## 候補の詳細

### 1. GCの第0世代の予算を広げる（RAM）

- 現状: 起動スクリプトはWorkstation／ServerとServerのヒープ数だけを指定できます。状態欄には世代別のGC回数と停止時間が出ています。
- 案: `DOTNET_GCgen0size`（16進のバイト数）を、起動するゲームプロセスだけに設定する引数を追加します。第0世代を大きくすると、確保したメモリを回収するまでの間隔が延び、RAMの使用量が増える代わりにGC回数が減ります。
- 確認が必要なこと: .NET 10の標準GCでこの設定がどこまで効くか、WaylithのカスタムCLR（`10.0.15-waylithclr.dev`）が環境変数を読むかは、静的には確定できません。既存のGC計測で、同じセーブ・同じ速度の10秒窓を比べれば判定できます。効かなければ引数を削除するだけです。
- 採用しないもの: ラージページ（`DOTNET_GCLargePages`）は、OSの特権設定とヒープ上限の固定が必要で、失敗時に起動できなくなるため候補にしません。

### 2. Vulkanパイプラインキャッシュを起動間で引き継ぐ（ディスク、RAM、CPU）

- 確認した事実: `Waylith.Rendering.MeshPipelineCache` は起動のたびに空の `VkPipelineCache` を作り、ディスクへ保存しません。メッシュ描画のパイプラインは、シェーダーの種類・描画状態・頂点レイアウトの組み合わせごとに、初めて描画するフレームで作られます。エンジンにはSPIR-Vを全コアで先に用意する `ShaderPrewarmer` がありますが、対象はシェーダーのコンパイルまでで、パイプラインの作成は含みません。
- 案: 終了時や一定間隔でキャッシュの中身を取り出して保存し、次回起動時に、保存した内容から作ったキャッシュをエンジンのキャッシュへ併合します（Vulkanの `vkGetPipelineCacheData` と `vkMergePipelineCaches`）。エンジンのキャッシュは置き換えず、追加するだけです。
- 不確実性:
  - エンジンが使うVulkanバインディング（`Brutal.Vulkan.dll`）にこの2つの関数があることは確認しました。キャッシュは描画器ごとに複数あり、描画は専用スレッドで進むため、併合には同期が必要です。
  - `MeshPipelineCache` のインスタンスと `pipelineCache` フィールドはprivateで、反射で到達する必要があります。
  - AMDやNVIDIAのドライバーは独自にディスクキャッシュを持つため、すでに同じ効果が出ている可能性があります。効果が小さければ採用しません。
  - ネイティブ呼び出しの誤りはプロセスの異常終了になります。ドライバーやGPUが変わった場合の無効化はVulkan側がヘッダーで判定しますが、ファイルの破損には自前の検査が必要です。
  - ポストエフェクトとコンピュートのパイプラインはキャッシュなしで作られており、この方法では対象外です。

### 3. 既存機能の上限を引き上げる（CPU、VRAM）

新しい処理は増やさず、すでにある処理の天井を設定で上げられるようにします。

- JIT先行コンパイル: 現在は最大8,000メソッド・最大2ワーカーの固定です。279個前後のMOD構成では対象メソッドがこれを大きく超えると見込まれます。上限とワーカー数を設定項目にします（WOWGAGのJIT準備が有効なときは従来どおり譲ります）。
- GPU先読みの画像サイズ: 初期1024px、プリセットで2048px、最大4096pxです。16 GBのVRAMでは、プリセットを4096pxまで上げる選択肢を加えられます。エンジンの退避しきい値（予算の約80%）より下に収める既存の上限はそのまま使います。
- 画面外区画の先行更新: 現在はポーズ中だけ、1フレーム1区画です。通常速度でもフレームガードの範囲で動かす選択肢を加えられます。WOWGAGが区画更新を置き換えている構成では従来どおり譲るため、WOWGAG併用時には効果がありません。

## 調査して、調整口がないと確認したもの

| 対象 | 確認した内容 |
| --- | --- |
| 区画メッシュのGPU転送 | 本体が再生成の時点で変換・登録し、エンジンが次のフレームでキュー全体を転送します。前倒しできる処理が残っていません（この前提の誤りにより、いったん実装した転送の前倒しを取り下げました）。 |
| エンジンのロード時先読み（`AssetPrefetcher`） | ワーカー数は「論理CPU数÷2−1、最大8」、保持量は64 MiBの定数です。MODの内容読み込み時に本体が呼びます。本MODの初期化より前に走り、値も定数のため変更できません。 |
| 音声のストリーミング判定 | 展開後2 MiBを超える音声はストリーミング再生になります。しきい値はエンジン内の定数です。 |
| VRAMの予算 | `WAYLITH_VRAM_BUDGET_MB` は上限を下げる方向にしか働きません。退避のしきい値は定数です。 |
| システムメモリへ退避したテクスチャの保持量 | ホスト側の予算の4分の1を超えるとディスクキャッシュへ戻します。しきい値は定数です。 |
| 共有ジョブプールのワーカー数 | 論理CPU数−1で固定です。設定口はありません。 |
| シェーダーのコンパイル | エンジンが起動時に全コアで用意します。本MODのゲーム内シェーダーキャッシュ先読みは、その後に要求される分にしか効きません。起動前の先読み（起動スクリプト）のほうが時機に合っています。 |
| GUIの文字（グリフ） | ImGuiのフォントが必要な文字を都度用意します。1文字あたりの負荷が小さく、先に全文字を作るのは本体が行わない新しい処理になるため候補にしません。 |
| ポートレート | キャッシュが1秒で期限切れになり、先に作っても使われません。 |

## 他MODとの関係で分かったこと

- 受領したWOWGAGのビルドには、ロード画面の間にエンジンの転送キューを空にする機能（`loadUploadInLoading`）、ロード中のポーン用グラフィック準備（`loadPawnGfxInLoading`）、JITの実行履歴の再生（`jitProfileReplay`）があります。ロード直後のフレームを軽くする処理はWOWGAGがすでに担当しているため、本MODが同じ領域に追加する余地は小さいと判断します。
- Overclockの自動ワーカー数は、16スレッドのCPUで7です。Overclock自身の説明に「16コアで7・11・15は同じ速度、23は遅くなった」とあり、ワーカーを増やしても速くならない領域があることを作者が記録しています。起動スクリプトで数を上げる場合は、この記述を前提にしてください。
- OverclockはWOWGAGの並列設定が1つでもONだと並列Pawn Tickを適用しません。両方を入れている場合、Overclockの `parallelThreads` を変えても効果はありません。
